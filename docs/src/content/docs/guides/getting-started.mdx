SAL projects are ordinary Git repositories with a `.sal` workspace for generated data.
The source files stay in your repository; the Iceberg table generated by SAL lives under `.sal/data`.

## Install SAL

Install the latest release, or update the one you have, with:

```sh
curl -fsSL https://raw.githubusercontent.com/cgs-earth/sal/main/install.sh | sh
```

The script downloads the prebuilt binary for your machine from the [latest GitHub release](https://github.com/cgs-earth/sal/releases/latest), checks it against the release's checksums, and installs it as `~/.local/bin/sal`, replacing an earlier one.
Set `SAL_INSTALL_DIR` to install somewhere else and `SAL_VERSION` (a tag such as `v0.1.2`) to pin a release.
Releases are published for Linux amd64 and macOS Apple Silicon on every push to `main`, and `sal --version` prints the release a binary came from.

On another platform, build from source with Go:

```sh
go install github.com/cgs-earth/sal@latest
```

DuckDB is linked into `sal` rather than shelled out to, so there is no DuckDB to install.
It is a C++ library, though, so building `sal` needs cgo and a C toolchain (`build-essential` on Debian or Ubuntu, the Xcode command line tools on macOS).
A binary built this way has no web UI for `sal serve --with-ui`, since the UI is built from its own sources with Node rather than committed; the release binaries carry it.

SAL also expects Git for project metadata.

## Initialize a repository

Run `sal init` from the root of a Git repository that already has a remote:

```sh
sal init
```

It asks for a sentence or two describing the project, which `--description` can give instead, and records it in `.sal/config.jsonld`; a directory that already has that file is already a project and `sal init` fails.
It also creates the local SAL data directory and adds `.sal/data` to `.gitignore`.
Generated data is not meant to be committed to source control.

Read more about the generated files in [Data Layout](/sal/reference/data-layout/).

## Add RDF files

SAL finds RDF files in the paths you pass to `sal validate` or `sal build`.
Use Turtle or JSON-LD for source data.

```sh
sal validate data/
```

Validation checks that RDF parses correctly and that prefixed terms resolve against their vocabularies.
If you need to remap vocabulary prefixes while validating, pass one or more `--prefix-maps` values.

## Build the data product

After source changes are committed, build the local Iceberg table, saying what the build changes the way a Git commit message does:

```sh
sal build --message "Add the station data" data/
```

The message is required, and is recorded in the snapshot the build commits.
By default, SAL writes an Iceberg table.
For validation-only workflows or debugging, see [`sal validate`](/sal/reference/commands/#sal-validate) and the `--format` option in [`sal build`](/sal/reference/commands/#sal-build).

## Query the result

Open the built table in the SQL shell:

```sh
sal query
```

SAL creates a `triples` view in the shell.
From there, run SQL such as:

```sql
SELECT subject, predicate, object
FROM triples
LIMIT 10;
```

Next, publish the generated table using [Publishing Data](/sal/guides/publishing-data/).
