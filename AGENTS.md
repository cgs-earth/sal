# SAL

SAL, (semantic accessibility layer), is a CLI tool for creating RDF data and metadata from a dataset. It contains a series of subcommands.

## Repository Structure

- sal is setup as a monorepo
    - `docs/` contains a documentation site written with Astro and Starlight on the overall project, any specifications, and sal commands at a high level
        - `docs/demos/` holds the VHS tapes for the terminal GIFs embedded in the command reference, plus the scripts that build `sal` and stage the demo project each tape records against. The GIFs are generated by CI rather than committed, so they can never show output the CLI no longer produces. See `docs/demos/readme.md`.
    - `examples/` contains examples of how to use sal or example sal module implementations
    - `.github/workflows` contains github workflows for CI/CD
    - Each sal subcommand is present in a folder of the same name. For instance -> `sal build` is present in the `build/` folder.
    - Any broadly reusable code is present in the `pkg` folder
    - `integration_tests/` contains integration tests which require spinning up additional services. They don't request real data from remote servers though.
    - `initialization` is an exception to the folder-per-subcommand pattern. This is since `init` is a keyword that can cause issues in golang.
    - `importation` is an exception for the same reason; `import` is a golang keyword. It owns the project ontology node of `.sal/config.jsonld` in both directions: the `sal import` subcommand writes it, and `build` reads it through `importation.ReadOntology`. `.sal/config.jsonld` is a single JSON-LD document with one `@graph` that condenses the project ontology and `build/validate`'s pinned vocabulary versions into one file; `pkg.PartitionConfigGraph` is what tells the two node kinds apart (a pinned vocabulary node carries `owl:versionIRI`, the ontology node never does), so each package can read and write its own nodes while carrying the other's forward untouched.
    - `salmodule/` is an exception to the folder-per-subcommand pattern. It holds the entire SAL Module specification implementation, in both directions:
        - the `sal salmodule` subcommand, which makes the sal CLI itself a sal module
        - dereferencing, building, and running the sal modules that a project references. `salmodule.Resolver` clones the module repository, builds its Dockerfile, and invokes the SAL Module CLI inside the resulting image.
        - This lives in `salmodule/` rather than `build/` because both `build` and `build/validate` need it. Do not duplicate docker or module resolution logic into either of those packages.
        - `salmodule.Default()` is the process-wide resolver shared by validation and build so that a module referenced from several places is cloned and built only once per invocation. Tests inject fakes through its `Runner` and `Command` fields and call `Reset` afterwards.
        - A module image is tagged with the git commit hash of the repository it was built from, and the resolver reuses images across invocations rather than only within one: `build` feeds the `urn:git-commit-hash:` pins from `.sal/config.jsonld` into the resolver through `UsePinnedCommit`, and a pinned commit whose image is still on the docker daemon is used without cloning or building anything (`--no-cache` skips this wiring so modules resolve from source again). Even without a pin, a clone whose HEAD already has an image skips just the docker build. A reused module still counts as resolved, so `Downloaded()` and `CommitHash` report it the same as a built one.

## Subcommands

### `build`

- Takes in RDF data, validates it, and writes it to a local iceberg table in the sal data directory.
    - All input RDF data should be validated. This RDF data can be defined in either Turtle or JSON-LD. 
    - For all input RDF data, if there is a term that is not defined in the provided prefixes, SAL will throw an error which calls out the specific line number with the offending term.
        - For instance, if the user makes a typo and specifies `schema:nameee` in their JSON-LD, SAL build will throw an error saying that `nameee` is not a defined term in the RDF vocab. This should be supported for any generalized RDF vocabulary.
    - Only new data should be written to the iceberg table. For instance, if the table already has a particular triple, it should be ommitted from the new commit. 
        - An identifier for each triple can be calculated by hashing the subject, predicate, object, the object's datatype (empty for an IRI or blank node object), and the object's language tag (empty for anything but an `rdf:langString`). This hash identifier can then be looked up in the iceberg table to check if it exists. The datatype and language are part of the identity because the table records them in `object_type` and `object_language`, so two literals with the same lexical form but different datatypes or language tags are distinct rows.
    - Build can also materialize triples from a sal module and add it to the iceberg table.
        - A sal module is another github repository with a Dockerfile in the root. 
            - More info on the sal module spec can be found here: @./docs/src/content/docs/reference/salmodule-description.mdx
            - An example sal module can be found here: @./examples/salmodule/python-geoconnex
        - A sal module is referred to in an rdf file by using the sal module ontology here: `https://w3id.org/sal/cgs-earth/sal-module-spec/salmodule#`
        - If a new term is defined in the sal module that is a subclass of `salmodule:NodeProcessor` the sal module should be built by fetching the remote git repository, building the docker container, and running it with the task instance passed through the environment variable the module's own ontology declares with `salmodule:taskInstanceEnvVar`. The JSON-LD that results from this process should be added to the in memory goRDFlib graph and thus added to the iceberg table upon a successful build. 
        - A task instance is configured in RDF, not with an embedded JSON-LD literal. `salmodule.ModuleOntology.TaskInstance` serializes the instance into the JSON-LD node object the module receives: every property of the instance whose predicate is in the module's own namespace becomes a key, and IRIs are written the way the module's ontology writes them (a module term becomes its relative name, any other IRI is shortened with a prefix the ontology's `@context` binds).
            - The serialized JSON-LD node object is what `salmodule:runCommand` documents; it is the input the run command is invoked with. `salmodule:taskInstanceEnvVar` only defines a constant, the name of the environment variable that value is carried in. Both are `owl:OntologyProperty` terms a module declares on its own ontology, and neither is written in a project's RDF; `build` warns and ignores `taskInstanceEnvVar` when a project sets it on an instance.
        - An example project using a salmodule might look like @./build/testdata/reference/ontology_with_sal.ttl 
        - An instance is only run when it is known to be a task. Either the project's RDF types it as a `salmodule:NodeProcessor`, `salmodule:NodeProducer`, `salmodule:NodeConsumer`, or `salmodule:Task`, or the module's own ontology declares its class as a subclass of one of those. A `salmodule://` typed instance that is neither is left alone.
        - A task writes newline delimited JSON, not JSON-LD, to stdout. The module ontology's `@context` must be injected into each node before it is converted to RDF, since it is what resolves the task output's keys to the module's vocabulary.
        - A relative IRI in a task's output resolves against the project base, never against the module's namespace. `GraphFromTaskOutput` takes the base explicitly and `MaterializeSalModules` passes the base of the graph being built, which is `pkg.DefaultSalBase()`. What a task produces is instance data owned by the project that configured and ran it; the module's namespace names its vocabulary. A module that wants its output under another namespace writes absolute IRIs, which are kept as written.
        - A task that emits `salmodule:Error` nodes instead of data fails the build with the messages the module reported.
        - Materialization happens in `build` only, after validation and after the uncommitted changes check, so that nothing is run for a build that would be rejected anyway.
    - Build pins the exact version of every vocabulary the project resolves against. See the `validate` section below for the store; `build` is what fills and writes it.
        - `build.projectVocabularies` opens `.sal/config.jsonld` for the project being built, or an ephemeral store when there is no SAL project to pin for. `--no-cache` sets `Refresh`, which resolves everything from source again and re-pins it.
        - `validator.PinDeclaredPrefixes` runs after the validation loop and resolves every prefix the source files declared, not only the ones a term was used from. A declared prefix that cannot be resolved fails the run.
        - `pins.Save` is called only after the uncommitted changes check, in the same place as import fetching and module materialization. `.sal/config.jsonld` is a git tracked file, so writing it before that check would leave the worktree dirty and make the next build refuse to run. `Save` is a no-op when nothing changed, which keeps a repeat build clean. It preserves the project ontology node the file already carries, since pins never inspects it.
        - `pins.AppendProvenance` runs right after `Save` and adds an `owl:Ontology` node with the same `owl:versionIRI`, `dcterms:format`, `dcterms:modified`, and `rdfs:comment` the config file records for every pinned vocabulary directly into the graph being built, so which exact version a build validated against is queryable in the triples table itself, not only recorded in `.sal/config.jsonld`. It runs after `NewTermsHaveClassDefinitions`, so this provenance is not subject to the project's own RDFS checks, the same way imported and module-materialized statements are not.
    - Build also merges in the ontologies the project imports. `build.ImportOntologies` reads the `owl:imports` IRIs out of the project ontology node in `.sal/config.jsonld` and resolves each one with `validate.PinnedGraph`, so that an imported ontology is carried by the data product at the version the project pinned rather than only referenced from it, as the project's own statements. It returns the IRIs it merged.
    - Every pinned vocabulary is carried by the table too, but marked as the vocabulary's rather than the project's. `build.PinnedVocabularyGraphs` parses every pin except the imported ones into a `load.VocabularyGraph{Namespace, Graph}` of its own, right after `ImportOntologies` and only for the iceberg format, and `ExportGraph` hands them to `load.WriteGraphToIceberg` beside the project graph. They never enter `finalGraph`, so `NewTermsHaveClassDefinitions`, `Run`'s returned graph, and the N-Quads export never see them. `load.tableRows` flattens everything into attributed rows: the project's triples first with `vocabulary` NULL, then each vocabulary in sorted namespace order contributing only hashes no earlier row has, so an asserted statement always wins and a statement two vocabularies share belongs to the first namespace. `triple_hash` does not include the column, and the diff in `load.diffGraphAgainstTable` compares it: a row whose hash is in the table but whose `vocabulary` differs is dropped and added again in the same snapshot. The `vocabulary` column is the newest, so `NewIcebergTableFromCfg` and `salsparql.VerifyObjectColumns` check for it and tell the user to `sal clean --wipe` and rebuild an older table. The STAC row count scans the whole table and includes these rows.
        - The project ontology's own statements do not arrive this way. The ontology node has no file of its own for the walk that collects source files to find, since `.sal` is skipped entirely and the node shares a file with pins. `build.projectOntologyContent` instead renders the node as a standalone JSON-LD document with `importation.SerializeOntology`, and `build.go`'s `Run` parses it directly with `validator.ParseContent` and folds its bytes into the source hash with `pkg.HashFilesAndContent`, so it is still validated, counted, and hashed like any other source file even though it is not one.
        - Fetching the imports happens in `build` only, in the same place as module materialization: after validation and after the uncommitted changes check. `validate` never fetches imports.
        - Imports are fetched with the same content negotiation and format sniffing a vocabulary lookup uses, but they are not cached; only vocabulary term sets are.
        - Not every import is an ontology document. An `oci://` import is pulled to `.sal/data/imports` and `dropImportStatement` takes its `owl:imports` statement back out of the graph, so nothing about the artifact reaches the table. A `salmodule://` import is a document like an `http` one, except that `validate.PinnedGraph` obtains it by cloning and building the module; its statements are merged like any other import's, and the module joins the ones `Resolver.Downloaded()` records in the table.
        - The imported statements are added after `NewTermsHaveClassDefinitions` has run, so an imported ontology is not subject to the project's own RDFS checks.
    - The last step of an iceberg build is `build.WriteProjectStacCatalog`, which writes a STAC catalog to `.sal/data/stac` from the committed table: `catalog.json` and `triples/collection.json`, the collection carrying the STAC Iceberg extension (`https://portolan-sdi.github.io/stac-iceberg-extension/v1.0.0/schema.json`) alongside the Table and Projection extensions. Everything is read from the table after it is written, not from the in-memory graph: the metadata location, snapshot, format version, partition spec, and columns from the metadata, and the row count and spatial extent from one scan of `object_geometry` (the summary's `total-records` does not subtract equality deletes, so the scan is what keeps the count exact). The directory is rewritten whole on every build and sits under `.sal/data`, not beside `.sal/config.jsonld`, because it names the current metadata file and would otherwise dirty the worktree after each build. `serve` serves it at `/stac/` and `clean --wipe` removes it. `push` and `upload` carry the directory as-is, so an uploaded copy still points at the local `file://` metadata path; rewriting it for a bucket is not done.

### `import`

- Records an external ontology on the project ontology node of `.sal/config.jsonld`, which `build` reads its `owl:imports` from. `sal import` creates the file if it does not exist, and creates the node if the file already exists only because a build has pinned vocabularies into it.
- The node names the project itself as `"@id": "."`, which resolves against `pkg.DefaultSalBase()`, the same base the project's own relative terms resolve against. `dc:title` defaults to the git project name and `--title` overrides it. `rdfs:comment` is always generated fresh, naming the git project, and is not user configurable.
- `importation` parses the node with `goRDFlib/jsonld.Parse` but renders it from a Go struct marshaled with `encoding/json`, so the generated shape stays flat and readable. A node carrying statements the struct does not cover is written back through `goRDFlib/jsonld.Serialize` instead, so hand written triples are never dropped. `importation.ReadOntology` and `writeOntology` isolate the ontology's own node from the rest of `.sal/config.jsonld`'s `@graph` with `pkg.PartitionConfigGraph`/`SplitJSONLDDocument`/`JoinJSONLDDocument`, so the pinned vocabulary nodes `build/validate` owns never affect ontology parsing, extra-statement detection, or serialization, and `writeOntology` re-reads the file and carries them forward untouched rather than overwriting the whole file.
- The file was Turtle headed by an autogenerated banner comment before it became JSON-LD; JSON has no comment syntax to carry that banner in, so the file no longer has one. The node is still regenerated on each import, so a hand edit still only survives when it is a statement the struct or the graph already carries.
- `importIRI` resolves what a reference was given as into the IRI recorded with `owl:imports`, and it accepts three kinds: an `http` or `https` URL, a `salmodule://` reference to a SAL module, and an `oci://` reference to an OCI artifact. A reference that names an artifact but omits the scheme is recognized by `looksLikeArtifactReference` so it can be reported as a missing `oci://` rather than as a malformed URL; anything else is reported as not a URL.
    - An `oci://` import is pulled to `.sal/data/imports` as it is recorded, so that an import missing from disk is restored rather than silently skipped, and `supersedeArtifactImport` drops the entry and the files of the version it replaces. It is the only kind dereferenced at import time; an `http` or `salmodule://` import is recorded and left for `build` to resolve.
    - A `salmodule://` import is an ontology document like an `http` one, so `build` merges its triples into the table; only where the document comes from differs. `validate.PinnedGraph` already dereferences the IRI by cloning and building the module, the same path a `salmodule://` vocabulary lookup takes.
    - A module is recorded under the IRI naming it, which is `ModuleRef.Namespace` without its trailing slash. Normalizing through `ParseModuleIRI` fills in the default host, so the same module written with and without it is recorded once; dropping the slash keeps a project that binds a prefix to the vocabulary base from having the `owl:imports` statement itself checked against the module's own terms. `PinnedGraph` parses the fetched document back against `Namespace`, for the same reason `vocabularyCache.parseBase` does.
- `.sal/config.jsonld` is a source file that belongs in git, and `build` treats the ontology node it carries as one, though the node has no file of its own; see `build.projectOntologyContent` in the `build` section above. `pkg.FindRdfDataInPaths` skips the `.sal` directory so that iceberg metadata under `.sal/data` is never mistaken for project RDF.
- `sal clean --wipe` removes `.sal/config.jsonld` along with the data product, so a wipe returns the project to the state it was in before anything was built or imported. It is removed even when there is no data product to delete, and `wipe`'s confirmation prompt names the file whenever it exists since it is a source file rather than a build artifact. The vocabulary documents the pins it carries name go the same way; `clean.removeProjectConfig` reads the pins to find them, since they sit under `.sal/data/blobs` rather than inside the table that a wipe removes wholesale.

### `validate`

- Validates RDF source files without committing anything. It runs the same pipeline as `build` with committing and sal project checks skipped, so any behavior described here applies to `build` as well.
- Every URI-backed term used in a file is checked against the vocabulary declared for its prefix. An undefined term is reported with the file, the line number, and the offending term.
- `validate.Validator` holds one `vocabularyCache` for a whole run, so a vocabulary is resolved once no matter how many files use it, and so `PinDeclaredPrefixes` can resolve every prefix the files declared once they have all been read. `ValidateRDFFile` is the single file wrapper around it.
- Declared prefixes are checked too, not only the terms used from them, and they are checked first: `build` parses every file with `Validator.ParseFile`/`ParseContent` before checking a single term with `Validator.Validate`, so the prefix checks and the prompt below run before any vocabulary is fetched. A vocabulary declared under namespaces that mix `http`/`https` or a trailing `/` or `#` is one error per vocabulary (`Validator.ConflictingPrefixes`, a `PrefixConflict` whose `Error` names every file and spelling); `build` logs each and returns the short `ErrConflictingPrefixes`. A namespace ending in neither `/` nor `#` is warned about and requires confirmation or `--allow-prefixes-without-slash-or-hash`; `Validator.PrefixesWithoutTerminator` reports them and `build.confirmPrefixesWithoutTerminator` owns the prompt, logging a refused prefix before returning `ErrPrefixRejected`. Both checks see `--prefix-maps` applied first, so a mapping is how a project reconciles a file it cannot edit.
- Vocabularies are resolved per project, never from a shared cache on the machine. `validate.PinnedVocabularies` owns the pinned vocabulary nodes of `.sal/config.jsonld` in both directions: it records a prefix's namespace against the SHA-256 of the document behind it as an `owl:versionIRI` of `urn:sha256:<hex>`, and stores that document under `.sal/data/blobs` named by the same hash. A `salmodule://` vocabulary is the exception: it is pinned by the git commit hash of the module repository instead, as `urn:git-commit-hash:<hex>` — see below. `LoadPinnedVocabularies` and `Save` use `pkg.PartitionConfigGraph`/`AssembleConfigGraph` to read and write only the nodes carrying `owl:versionIRI`, carrying the project ontology node `importation` owns forward untouched.
    - `.sal/config.jsonld` belongs in git; the documents its pins name do not, since `sal init` gitignores `.sal/data` and they travel with the data product instead. That split is why `push` and `upload` carry them with no changes of their own.
    - `PinnedVocabularies.AppendProvenance` writes the same `owl:versionIRI`/`dcterms:format`/`dcterms:modified`/`rdfs:comment` statements `.sal/config.jsonld` carries directly into a `*rdflibgo.Graph`, so `build` can commit them to the triples table as provenance. It is the only place that shape is duplicated; `nodes` (the config file writer) and `AppendProvenance` (the graph writer) must be kept in sync by hand since one writes JSON and the other writes RDF triples; `pinnedVocabularyComment` is the one place the `rdfs:comment` text itself is generated, shared by both.
    - The pin is keyed by the prefix namespace, not the document URL, since that is what a project declares. `vocabularyDocumentURL` still decides what is dereferenced, and the store memoizes by that URL so two namespaces served by one document are fetched once.
    - A pin whose document is missing or no longer hashes to the pinned version is fetched again rather than failing, since a fresh clone has the lockfile before it has the documents.
    - `build/vocab` holds bundled copies used when a document cannot be fetched or parsed. The bundled copy is what validation used, so it is what gets pinned. A pinned document that no longer parses is an error instead, since falling back would defeat the pin.
    - `EphemeralVocabularies` is the store that pins nothing. Validating RDF outside a SAL project uses it, and so do the unit tests, which replace its `Fetch`.
- A `salmodule://` prefix is a vocabulary like any other, but it is not served over HTTP. It is dereferenced by cloning the module repository, building its Dockerfile, and running the module's ontology command; the JSON-LD the module prints is the vocabulary document.
    - The module ontology's relative terms resolve against the module's own `salmodule://` namespace, not against the sal project's base. `vocabularyCache.parseBase` is what keeps these apart; passing the project base here would make every module term fail to match.
    - A `salmodule://` vocabulary is pinned by the git commit hash of the module repository's HEAD at clone time, not by the SHA-256 of the ontology document `PinnedVocabularies.Pin` would otherwise derive. `salmodule.Resolver.image` reads the hash with `git rev-parse HEAD` right after cloning, and `FetchOntologyDocument` reports it alongside the document so `validate.fetchVocabularyDocument` can pin it at `urn:git-commit-hash:` instead of `urn:sha256:`. The reason is that a module's task logic can change without its ontology document changing, and that is a change a build should still be able to tell apart. The document itself is still stored under `.sal/data/blobs`, just named by the commit hash rather than a content digest, so it cannot be re-verified against its pinned version the way a SHA-256 pin can; its presence on disk is trusted instead.
    - This means validating a file that references a module clones and builds that module. That is intended, and matches the dereferencing sequence in the SAL Module spec. Once the project has pinned the ontology the module reported, a later build resolves it from the pin instead of building the module again to ask.
    - Validation never runs module tasks. Only `build` invokes the run command. A task's output is data rather than vocabulary, so materialization is never resolved from a pin.

### `clone`

- Takes in a full URL to an OCI artifact. 
- It uses the oras golang to introspect the manifest info about the artifact. It retrieves the value of the `org.opencontainers.image.source` to determine the location of the source code. It finds the pinned commit hash using the value of `sal.git-commit-hash`.
    - It then clones the source code into the current working directory.
    - It checks out the commit hash specified in the manifest.
    - Within the newly cloned repo directory, it should run `sal init` to initialize a sal project.
    - Within the new cloned repo directory, it should pull the OCI artifact and place it in the `.sal/data` directory.

### `edit`

- Rewrites Iceberg table metadata so a built table can be read from a new table root.
- `edit.RewriteIcebergTableRoot` must update every Iceberg metadata file that can contain paths: `*.metadata.json`, manifest list Avro files, and manifest Avro files.
    - JSON metadata contains fields such as `location`, `manifest-list`, and `metadata-file`.
    - Avro metadata contains fields such as `manifest_path` and data file `file_path`.
- The edit command must not rewrite Parquet data files. It only changes metadata references.
- Path rewriting is prefix based: the old table root is replaced by the new table root, and child paths under the old root are preserved.
- `edit.RewriteIcebergMetadataPath` exists for upload-time metadata renames. Use it when a single metadata object name changes and every reference to that exact metadata path must be updated.

### `upload`

- upload copies `.sal/data` to a temporary staging directory, rewrites the staged Iceberg metadata, and uploads the staged files. The local `.sal/data` directory must remain unchanged.
- upload uses the edit package for Iceberg metadata rewrites. Do not duplicate JSON or Avro metadata traversal logic in upload unless the edit package cannot represent the operation.
- Bucket URL semantics are important:
    - A bare object-store bucket like `gs://my-bucket/` uploads the full `.sal/data` layout. If the local table is `.sal/data/sal/triples`, the uploaded table root is `gs://my-bucket/sal/triples`.
    - An explicit object-store path or prefix like `gs://my-bucket/sal/triples` or `gs://my-bucket?prefix=sal/triples/` is treated as the table root when there is exactly one Iceberg table.
    - `https://storage.googleapis.com/<bucket>/...` is a supported GCS-compatible URL form. upload must upload through the GCS blob driver but write `https://storage.googleapis.com/<bucket>/...` paths into Iceberg metadata so S3-compatible tooling can resolve the table through HTTPS.
    - Multiple Iceberg tables always preserve their relative table paths under the bucket root or prefix.
- Upload ordering matters for readers: data files first, metadata files second, and `metadata/version-hint.text` last.
- Object-store uploads (`gs`, `s3`, `azblob`, and `https://storage.googleapis.com`) must use fresh metadata object names during upload. Reusing the same Avro manifest object names can leave DuckDB or HTTP/object-store caches reading stale manifests after a reupload.
    - Fresh upload metadata includes renamed Avro metadata files, updated references to those renamed files, a new `v<number>.metadata.json`, and a `version-hint.text` pointing to that version.
    - `version-hint.text` must not include a trailing newline; DuckDB treats the newline as part of the version string.
- Percent escaping depends on the table root scheme:
    - Do not percent-escape Iceberg `file_path` values for `gs://`, `s3://`, or `azblob://` metadata roots. The object-store client handles URL encoding when fetching the object.
    - Do percent-escape child path suffixes for literal `http://` or `https://` metadata roots. Local partition directory names may contain literal percent-encoded values like `predicate_partition=http%3A%2F%2Fschema.org%2Fte`; in an HTTPS URL these percent signs must become `%25` so the remote object key resolves correctly.
- The key upload verification query is:

```sql
SET enable_object_cache = false;
SELECT
    subject,
    predicate,
    object
FROM iceberg_scan(
    'gs://sal-test-bucket/sal/triples'
)
LIMIT 5;
```


### `serve` 

- Starts a local HTTP server on port 8080.
- The server can resolve SPARQL queries against the iceberg triples table
    - The same SPARQL Protocol query operation is also served at `/v{snapshot}/sparql`, where `{snapshot}` is an Iceberg snapshot ID, reading the table as it stood at that snapshot. `salsparql.SnapshotRunner` is the surface it needs on top of `Runner`: `HasSnapshot` asks `iceberg_snapshots()` on every request rather than caching, so a snapshot a build commits while the server runs is queryable without a restart, and `AtSnapshot` returns a `DuckDBRunner` with `SnapshotID` set. A snapshot the table does not have, or a version that is not a snapshot ID, answers 404.
    - A snapshot runner's `Translate` scans `iceberg_scan(<table>, allow_moved_paths = true, snapshot_from_id = N)` in place of the `triples` view for every triple pattern (`tableSources.source` in `translate.go`, which also resolves the endpoint a `SERVICE` names), rather than registering a view per snapshot, so the translated SQL says which snapshot it reads. `ToSQL` itself is unchanged; `toSQL` is the same translation over any source.
    - A `SERVICE <endpoint> { ... }` clause is supported only when the endpoint is one of this server's own, recognized by path alone (`/sparql` or `/v{snapshot}/sparql`, in `translate.go`'s `servicePath`, which must agree with the routes `serve` registers): its triple patterns scan the table at that snapshot while the rest of the query scans the runner's own, so one query joins and compares two snapshots. Nothing is fetched over HTTP, and any other endpoint is an error rather than a federated query. goRDFlib rejects `SERVICE` at parse time but parses `GRAPH`, so `rewriteService` turns `SERVICE <iri>` into `GRAPH <urn:x-sal-service:iri>` before parsing and `basicGraphPatternParts` reads the marked `GraphPattern` back as a service; an unmarked `GRAPH` stays unsupported. The SPARQL tab's **Added since previous snapshot** and **Removed since previous snapshot** samples are built in `SparqlTab.tsx` from the Stats snapshot listing, since they need a snapshot ID only the server knows and the page's own origin for the endpoint IRI.
    - `MINUS { }` and `FILTER [NOT] EXISTS { }` translate to an `EXISTS` subquery correlated to the enclosing query through shared variables (`translator.subquerySQL`), which is what makes a snapshot diff possible; a join cannot express "absent from the other snapshot" and pairs every value of a multi-valued predicate with every other. A subject or predicate correlates by column, an object by rendered text plus `object_language` and `object_type` under `IS NOT DISTINCT FROM`, and a whole `?s ?p ?o` pattern against one enclosing scan by `triple_hash` alone (`correlationSQL`), which is exact and needs no spatial load. `translator.graphPatternParts` flattens a group into `groupParts`: triples, filters, and `minusGroup`s that remember the variables of the group before the MINUS, since the parser nests `{ A MINUS { B } C }` as `Join(Minus(A, B), C)` and SPARQL subtracts B from A alone; a MINUS sharing no variable subtracts nothing, and its filters see only its own variables, whereas EXISTS is correlated on and its filters see everything in scope. A group nested inside a SERVICE is read from that endpoint by wrapping it in the marked `GraphPattern` again (`scopeExists`).
    - `serve.snapshotSparqlHandler` matches `^/v([^/]*)/sparql$` by hand on the root route and falls through to whatever else the root serves. It is not a ServeMux pattern because a wildcard has to be a whole path segment, so it cannot carry the `v`, and a bare `/{version}/sparql` conflicts with the `/blobs/` prefix. There is no UI tab for the versioned route, so with `--with-ui` it is the API whatever asked for it.
- `--with-ui` additionally serves a React web UI at `/` plus the JSON endpoints it reads: `POST /api/sql`, `POST /api/sparql/translate`, `GET /api/stats`, `GET /geometries`, and `GET /geometries/extent`.
    - The SPARQL tab has a **Show SQL** toggle that opens a read-only pane (`serve/sal-ui/src/tabs/sparql/SqlPreview.tsx`) with the SQL the query translates to, fetched from `/api/sparql/translate` as the query is edited. The pane is a debugging aid, never an editor. It sits beside the Yasgui editor when `.sparql-workspace` is wide enough, decided by a CSS container query rather than the viewport, and below it otherwise.
    - The UI source lives in `serve/sal-ui/`. It is a Vite + React + TypeScript app using a high contrast Catppuccin Mocha palette, `@zazuko/yasgui` for the SPARQL editor, and CodeMirror 6 for the SQL editor.
    - `serve/ui.go` embeds `serve/sal-ui/dist` with `//go:embed`, so that build output is committed to git rather than gitignored. `go install` must be able to produce a working UI without a Node toolchain.
    - Rebuild it with `make ui` after changing anything under `serve/sal-ui/src`. `.github/workflows/ui_build.yml` fails if the committed `dist` does not match the sources.
    - The Map tab is a MapLibre map over `GET /geometries` and `GET /geometries/extent`. It draws either the last result of the SQL or SPARQL tab, which both publish into the `serve/sal-ui/src/results.ts` store, or a bounding box query of its own; `geo.ts` turns a tabular result into features by parsing any WKT or GeoJSON cell with `betterknown`, with the other columns as properties. The map reads only; it never goes through iceberg-go.
    - `query/sparql/geometries.go` owns the geometry queries. The `object_geometry` column arrives from DuckDB's Iceberg reader as `GEOMETRY` already, so it goes straight into the `ST_` functions; do not wrap it in `ST_GeomFromWKB`.
    - `serve/ui.go` gzips the embedded assets once at startup and serves them precompressed with `Vary: Accept-Encoding`. Do not precompress at `make ui` time instead: `ui_build.yml` diffs the committed `dist` against a fresh `npm run build`, so committed `.gz` files would have to be byte reproducible.
- DuckDB execution and the SQL behind each `sal query --info` option live in `query/sparql`, not in `serve` or `query`. `salsparql.InfoSQL` and `DuckDBRunner.RunSQL`/`Stats`/`Geometries` are shared by the `query` subcommand, the SPARQL shell, and the serve endpoints. Do not duplicate those queries.
    - DuckDB is the `github.com/duckdb/duckdb-go/v2` library linked into the binary, not the `duckdb` CLI shelled out to. Nothing in sal may exec `duckdb`; there is no CLI to find. `query/sparql/duckdb.go` owns the whole surface: the shared handle, the `triples` and `triples_all` views, extension loading, and reading rows.
    - `triples_all` is the whole table and `triples` is `triples_all WHERE vocabulary IS NULL`, the statements the project itself makes. `projectRowsFilter` in `duckdb.go` is the one definition of that filter; the only other places it is written are `snapshotScanSQL`'s callers, since `iceberg_scan` at a snapshot is scanned inline: `SnapshotSQL`/`SnapshotDiffSQL` add it to their own SELECTs and the translator adds `<alias>.vocabulary IS NULL` per scan through `tableSource.clause`, never by wrapping the scan in `SELECT *`, which `needsSpatial` would take for a geometry projection. An imported data product built before the column is registered without the filter as a fallback.
    - Reasoning is a per-call `bool` on `Runner.Run` and `SQLTranslator.Translate`, not runner state, so one server answers both kinds of request on one runner and `AtSnapshot` has nothing to carry; it reaches `tableSources.reasoning`, and a `SERVICE` inherits it. It is confined to the RDFS schema predicates: `translator.schemaPattern` says whether a pattern's predicate, or every predicate of its path step, is in `rdfsSchemaPredicates` (`rdfs:subClassOf`, `subPropertyOf`, `domain`, `range`), and only such a pattern under reasoning reads `triples_all` or the snapshot scan unfiltered; a variable predicate, a negated set, and every other pattern read the project's own rows whatever the setting. This is what keeps a vocabulary's own instances and class declarations, hundreds of them in schema.org, out of every result: its terms reach a result only through a hierarchy a query walks. The surfaces are the `reasoning` request parameter (`serve.reasoningParam`), `sal query --sparql --reasoning`, the `reasoning` field of `/api/sparql/translate`, and the UI's Reasoning toggle, which Yasgui sends through `requestConfig.args` read from a ref so toggling never rebuilds the editor.
    - The library is cgo, so `CGO_ENABLED=0` cannot build sal. The DuckDB library itself is linked statically, but the binary is not fully static: DuckDB `dlopen`s its extensions, which a statically linked glibc cannot do, so libstdc++ and glibc stay dynamic.
    - `duckdbInstance` is the process-wide handle every query runs through, opened on first use. Opening DuckDB and loading its extensions costs far more than any query sal runs, so a process pays for it once. Do not open a second handle per query or per request; `sal serve` answers everything on this one.
    - Extensions are downloaded from extensions.duckdb.org on first use, since only `parquet`, `json`, `icu`, and `core_functions` are linked in. `sal duckdb-extensions` primes that cache; it is hidden from help and exists for the Dockerfile and the demo recordings to call.
    - `RunSQL` wraps every statement in `SELECT COLUMNS(*)::VARCHAR FROM (...)` so DuckDB renders each value to text itself. The driver returns Go values, and `GEOMETRY`, `DECIMAL`, `LIST`, and `STRUCT` have no Go equivalent that formats the way DuckDB does. Do not hand-roll that formatting in Go. The wrapper preserves both the inner statement's column names and its `ORDER BY`, which `InfoSQL("snapshots")` depends on.
    - Statements run one after another on the shared handle. There is no batching layer any more: `RunSQLBatch` existed only to amortize process startup across `Stats`'s four queries, and with DuckDB linked in there is no startup left to amortize.
    - The spatial extension is loaded on demand, not at open. It is around 60 MB and DuckDB cannot autoload it. `needsSpatial` decides: the `ST_` functions need it, and so does anything projecting the `object_geometry` column, which DuckDB exposes as `GEOMETRY` and cannot read without it. A statement that needs spatial in some way `needsSpatial` misses is retried once with it loaded, so widening the check is a performance fix, never a correctness one. Once loaded it stays loaded for the life of the process.
- SPARQL is answered by translating it to SQL in `query/sparql/translate.go`. `DuckDBRunner.Translate` is the one place the whole SPARQL-to-SQL step lives, `ToSQL` plus the runner's own `LIMIT` when the query states none; `Run`, the shell's F2 page, and `/api/sparql/translate` all go through it, so the SQL shown anywhere is exactly the SQL that runs. `geosparql.go` maps the GeoSPARQL `geof:` FILTER functions that have a direct DuckDB spatial analog (the `sf*` relations, `distance`, and the geometry constructors that take only geometries) to the `ST_` function of the same meaning; a function without one is an error, never an approximation. A projected object renders `object_geometry` as WKT through `ST_AsText`, which is what loads the spatial extension; joins and comparisons keep the geometry-free `bindingExpr` so they never do.
    - Property paths live in `query/sparql/paths.go`. `translator.pathSteps` reduces a `paths.Path` to `patternTriple`s each carrying a `pathStep` (predicates, negated, inverse, zero/more): a sequence becomes patterns chained through hidden `?__sal_path<n>` variables, which `patternSQL` keeps out of `discovered` so `SELECT *` never projects them; an inverse swaps which column the subject and object read; an alternative or negated set is `predicate IN`/`NOT IN` (`predicateClause`); and a repeated step scans `closureSQL`, a derived table with `start`/`finish` columns holding the closure of the step's edges from a recursive CTE (`UNION`, which terminates cycles), plus for `*` and `?` the identity of the endpoint already bound (`closureIdentity`: a constant, or an earlier or enclosing scan's expression joined `LATERAL`), falling back to the nodes the edges touch. The CTE sits inside the derived table so the outer `SELECT` stays first, which the `SELECT DISTINCT` rewrite and `textQuery`'s wrapper rely on. The closure is computed whole, correct but potentially slow over a large instance predicate. goRDFlib parses `(^p)+` but not `^p+`.
- `sal query` opens the `query/sparql` shell in SQL mode, and `sal query --sparql` opens the same shell in SPARQL mode. `shellMode` is the only difference: it selects the editor's language and highlighter, its history directory, and whether the F2 page showing the translated SQL exists. SQL mode runs the statement it opened on so that `sal query --info snapshots` shows the snapshots straight away.

## Code Style

- Use testify for writing succinct tests; avoid just the standard library and if statements with `t.Error()`.
- If a function would only be called from one other function and it is short, try to just condense it into the function that calls it.
- Any function with functionality that is non trivial should be documented with a succinct comment of what it does.
- Don't create functions that are very small and only used in a single place.
- Prefer to not use table oriented tests unless there is significant test duplication; make each test case a separate test function so it is easier to debug and isolate failures.
- All tests should be unit tests without external fetches to remote servers. All local filesystem operations should be mocked or written to tmp files. 

## Boundaries

* Ask First:
    - Large cross-package refactors.
    - If some functionality would be very complex, duplicative, and better handled by an underlying library like json-gold or goRDFlib, explicitly call it out; don't try to create a custom fix here with lots of specialized code
    - If the AGENTS.md file should be updated to reflect new changes, explicitly call it out

## Development 

- `go test ./...` should pass after every new feature
- For any major new user facing features, add associated documentation in the `/docs` folder
- Use ripgrep via `rg` instead of grep if it is present to speed up searching through the codebase
