# SAL

SAL, (semantic accessibility layer), is a CLI tool for creating RDF data and metadata from a dataset. It contains a series of subcommands.

## Repository Structure

- sal is setup as a monorepo
    - `docs/` contains a documentation site written with Astro and Starlight on the overall project, any specifications, and sal commands at a high level
        - `docs/demos/` holds the VHS tapes for the terminal GIFs embedded in the command reference, plus the scripts that build `sal` and stage the demo project each tape records against. The GIFs are generated by CI rather than committed, so they can never show output the CLI no longer produces. See `docs/demos/readme.md`.
    - `examples/` contains examples of how to use sal or example sal module implementations
    - `specs/` holds human-editable specification sources, kept at the top level so they can be edited without touching code. `specs/salmodule.ttl` is the SAL Module ontology in Turtle, the document published at `https://w3id.org/sal/salmodule#`; the docs site renders it verbatim on the "SAL Module TTL Spec" page, and `salmodule/module_ref.go` mirrors its ontology properties as constants. Nothing in Go reads that file. `specs/salmodule-ontology.schema.json` is the JSON Schema for a module's ontology document, which the docs site renders on the "SAL Module JSON Schema" page and the `specs` Go package embeds as `specs.SalModuleOntologySchema`; `sal init --salmodule` copies it to `.vscode/salmodule-ontology.schema.json` and registers it for `ontology.jsonld` in `.vscode/settings.json` (`initialization.writeEditorSchema`). `sal validate --salmodule` (`salmodule.CheckModule`) validates a module's own `ontology.jsonld` against it, so the rules the editor applies are the ones sal applies; the document a referenced module prints is never checked against it, `salmodule.parseModuleOntology` parses that as RDF and nothing more. It fixes what the SAL Module specification fixes (the `@context` prefixes, one `owl:Ontology` node named `.`, at least one direct subclass of a `salmodule:` task class, IRI references written as `{"@id"}`, typed SHACL Core parameters, and the constraints `salmodule/stream_shape.go` refuses on a `stdoutShape` or `stderrShape`) and leaves every other node and key open. Keep it in step with what `parseModuleOntology`, `TaskInstance`, and `StreamValidator` read, and with the skeleton `initialization.salModuleOntology` writes; `specs/specs_test.go` checks the example module and `salmodule/sal_ontology.jsonld` against it, and `initialization_test.go` checks the scaffold.
    - `.github/workflows` contains github workflows for CI/CD
    - Each sal subcommand is present in a folder of the same name. For instance -> `sal build` is present in the `build/` folder.
    - Any broadly reusable code is present in the `pkg` folder
        - sal is on goRDFlib v0.9, where every graph method takes a `context.Context` and returns an error, and `Triples`/`Namespaces` yield `(value, error)` pairs, so that a persistent store can report a failure. Every graph sal builds is in memory (`MemoryStore` or `pkg/compactstore`) and cannot fail, so graph calls go through the helpers in `pkg/graph.go` (`pkg.Triples`, `pkg.AddTriple`, `pkg.SetTriple`, `pkg.RemoveTriples`, `pkg.GraphLen`, `pkg.Contains`, `pkg.Bind`, `pkg.Namespaces`, `pkg.ListItems`), which use a background context and panic on the error that cannot happen, rather than threading errors through every callback. Call the graph directly only when a context and an error path are genuinely there. Parsers and serializers (`turtle.Parse`, `jsonld.Parse`, `nq.Serialize`, ...) do real I/O and are called directly with a context, the caller's where one is in scope and `context.Background()` otherwise, and their errors handled. `jsonld.Parse` gives every call its own blank node scope, so parsing documents one at a time into a shared graph is safe.
        - `pkg/compactstore` is a goRDFlib `store.Store` that holds a graph in a fraction of the memory `rdflibgo.MemoryStore` does: every distinct term is interned once, a triple is three 32-bit ids, and the indexes are postings lists per term, where MemoryStore keeps three nested maps with the triple at every leaf and pays several hundred bytes for each of the singleton inner maps a unique literal object makes (around three times the memory for a million triples; most of what remains is the terms themselves). `build.go` makes the graph a build gathers its sources, imports, and provenance in on it (`rdflibgo.WithStore(compactstore.New())`; what module tasks produce never enters it, see `load.Spool` below); everything else, the per-document graphs validation parses, module ontologies, and so on, stays on the default store. A removed triple is tombstoned and compacted away once tombstones outnumber live triples (`compactionMinimum` guards small stores), which is what blank node stabilization's remove-then-add rewrite relies on. Like MemoryStore it holds the read lock for the whole of an iteration, so a graph must not be mutated from inside one. It holds one unnamed graph and ignores the graph argument (`ContextAware` is false); the only error it returns is a done context's. `TestStoreAgreesWithMemoryStore` checks it against MemoryStore over random operations and `TestStoreConformance` runs goRDFlib's `storetest` suite; keep both passing rather than special-casing either.
    - `integration_tests/` contains integration tests which require spinning up additional services. They don't request real data from remote servers though.
    - `initialization` is an exception to the folder-per-subcommand pattern. This is since `init` is a keyword that can cause issues in golang. Besides `.sal/data`, `sal init` creates the project's `sparql/` directory, which is source and so is not gitignored, adds `.sal/data` and `.sal/constructed` to `.gitignore`, leaving an entry the file already has alone, and writes a `Makefile` (`initialization.projectMakefile`, left alone when one exists) that documents the sal commands a project runs plus `make plan/apply/destroy/upload` over the `terraform/` directory; it is documentation that runs, not a build system. `--with-iac` also writes that directory through `terraform.Generate`, leaving an existing configuration alone with a warning. It also writes the project node of `.sal/config.jsonld` (see the `import` section below): `"@id": "."` typed `schema:Project` with the description as `dcterms:description`, which is required, asked for with the one-line prompt `Description of the project:` (an empty answer is asked again, and input running out is `ErrDescriptionRequired`) or given with `--description`. The prompt comes before anything is written, so giving up leaves nothing behind. A directory that already has `.sal/config.jsonld` is an initialized project and `sal init` fails rather than write over it. `sal init` also seeds the common vocabularies (`validate.CommonVocabularies`: rdf, rdfs, owl, dcterms, dc, schema.org, sosa, ssn, qudt, skos, foaf, prov, dcat, geosparql, time, shacl) into `.sal/data/blobs` through `validate.SeedVocabularies` unless `--no-vocabularies` (`sal clone` passes it, since the artifact brings its own blobs). A seed is a document named by its SHA-256 plus an entry in `blobs/seed.jsonld`, **not a pin**: nothing is written to `.sal/config.jsonld` until a build uses the namespace, when `PinnedVocabularies.Document` pins the seeded document instead of fetching it (`--no-cache`/`Refresh` ignores seeds, and a seed whose file no longer hashes is fetched). A seed must parse as RDF and define a term in its own namespace, so an HTML error page is never stored. Failures only warn. Tests replace `validate.SeedFetch` (`newGitRepo` makes it fail offline). `sal init --salmodule` creates none of that project layout, since a module is not a project; it only checks the git remote and scaffolds the module files (`salmodule.WriteModuleFiles`, `salmodule.WriteEditorSchema`), and asks for no description. By default it writes `ontology.jsonld` from the browser form, which is `edit.Form` served in mode `init` and so also edits an `ontology.jsonld` the module already has; `InitCmd.opensForm` takes the prompts instead with `--no-ui` or `--bare`, or when `pkg.HeadlessReason` says no browser is likely to open (`CI` set, an SSH session, stdout not a terminal, no display on Linux), and `--ui` forces the form. Tests replace `pkg.HeadlessReason` so a module is initialized at the prompt.
        - `sal init` also installs the agent skill under `skills/` that fits what it initializes: the `sal` skill into a project and the `salmodule` skill into a module (`InitCmd.installSkills`), unless `--no-skills`. `pkg.InstallSkills` clones `pkg.SkillsRepository` (the sal repository; tests point it at a local one through `pkg/skillstest`, and `newGitRepo` does so for every init test so none reaches GitHub) shallow and sparse to `skills/` and copies the skill into every `pkg.SkillDirs` entry, `.claude/skills` and `.agents/skills`, duplicated until the agents agree on one directory. A download that fails only warns, since the project is initialized by then; `sal init --skills` in an initialized project installs the skills and nothing else, and there the failure is the error. Scripts that run `sal init` where nothing reads the skills (`entrypoint.sh`, the demo scenario, the integration test) pass `--no-skills`. Prompts share one `bufio.Reader` over `stdin` (`prompts()`), since a second reader over the same source would miss what the first buffered.
    - `construct/` holds the `sal construct` subcommand and everything about the CONSTRUCT queries in `sparql/` that does not need a build: finding them, running them through a `construct.Runner`, and writing `.sal/constructed`. `build` imports it for the same step inside a build; `construct` must never import `build`.
    - `importation` is an exception for the same reason; `import` is a golang keyword. It owns the project node of `.sal/config.jsonld` in both directions: `sal init` and the `sal import` subcommand write it through `importation.WriteOntology`, and `build` and `serve` read it through `importation.ReadOntology`. `.sal/config.jsonld` is a single JSON-LD document with one `@graph` that condenses the project node and `build/validate`'s pinned vocabulary versions into one file; `pkg.PartitionConfigGraph` is what tells the two node kinds apart (a pinned vocabulary node carries `owl:versionIRI`, the project node never does), so each package can read and write its own nodes while carrying the other's forward untouched.
    - `salmodule/` is an exception to the folder-per-subcommand pattern. It holds the entire SAL Module specification implementation, in both directions:
        - the `sal salmodule` subcommand, which makes the sal CLI itself a sal module
        - dereferencing, building, and running the sal modules that a project references. `salmodule.Resolver` clones the module repository, builds its Dockerfile, and invokes the SAL Module CLI inside the resulting image. `runCommand` runs git with `GIT_TERMINAL_PROMPT=0` and the askpass variables cleared, so a private or missing repository fails with advice about credential helpers instead of blocking on a prompt the captured output hides (an IDE terminal's askpass helper makes that a popup nobody notices); a credential helper holding a token is still used.
        - This lives in `salmodule/` rather than `build/` because both `build` and `build/validate` need it. Do not duplicate docker or module resolution logic into either of those packages.
        - `salmodule.Default()` is the process-wide resolver shared by validation and build so that a module referenced from several places is cloned and built only once per invocation. Tests inject fakes through its `Runner` and `Command` fields and call `Reset` afterwards.
        - A module image is tagged with the git commit hash of the repository it was built from, and the resolver reuses images across invocations rather than only within one: `build` feeds the `urn:git-commit-hash:` pins from `.sal/config.jsonld` into the resolver through `UsePinnedCommit`, and a pinned commit whose image is still on the docker daemon is used without cloning or building anything (`--no-cache` skips this wiring so modules resolve from source again). Even without a pin, a clone whose HEAD already has an image skips just the docker build. A reused module still counts as resolved, so `Downloaded()` and `CommitHash` report it the same as a built one.

## Subcommands

### `build`

- Takes in RDF data, validates it, and writes it to a local iceberg table in the sal data directory.
    - Every build records a `--message` (`-m`), like a git commit message. `BuildCmd.resolveMessage` settles it before anything is read or fetched: the flag when given, else the full message of the commit HEAD is at (`pkg.GitCommitMessage`, `git log -1 --pretty=%B`, a var in `run.go` tests replace), written back to `cfg.Message` and logged, since a build of a clean worktree is a build of that commit. A build of a dirty worktree, which only `--force` allows, matches no commit, and a repository with no commit has none to take, so both return `build.ErrMessageRequired` without a flag, and the error points at `sal validate` as the way to check the project without committing; `sal validate` (`skipCommit`) needs none. `sal run` has the same flag and passes it through to the build it makes, so it falls back the same way. The message travels `ExportGraph` → `load.WriteGraphToIceberg`/`StagedGraph.Commit` → `commitGraphDelta`, which writes it into the snapshot summary under `pkg.SnapshotMessageProperty` (`sal.message`) through `NewRowDelta`'s snapshot properties, next to the triples the commit added and removed under `pkg.SnapshotTriplesAddedProperty`/`SnapshotTriplesRemovedProperty` (`sal.triples.added`/`sal.triples.removed`), which `commitGraphDelta` adds to every commit it makes; a build that changes nothing commits no snapshot and warns that the message was dropped, and the staging commit carries no message. `salsparql.InfoSQL("snapshots")` reads them back from the `snapshots` array of the latest metadata file, as `triples_added`, `triples_removed` (falling back to Iceberg's `added-records` and `added-equality-deletes` for a snapshot written before sal recorded its own), and `message`, followed by `git_commits` (the tags on the snapshot; `pkg.SetTagOfLatestSnapshot` tags the current snapshot with HEAD after every build, including one that committed nothing, which is what `sal run`'s `verifyTableMatchesCommit` checks, so a snapshot can carry several) and `metadata_file`, the lowest-version metadata file naming the snapshot as current, read over every metadata file of the table (`metadataFiles`; an `https://` table cannot be listed, so there only the latest file is read); the manifest list and the raw summary are not projected. That result is what `sal query --info snapshots` prints and what the UI's Stats tab draws by column name in `serve/sal-ui/src/components/SnapshotsTable.tsx` (timestamp to the minute, the counts as `+n −m`, each commit as its full hash on its own line, and a **Query** column whose two buttons `visit` a share link into the SQL tab, with an `iceberg_scan` at `snapshot_from_id`, or the SPARQL tab, with a `SERVICE` on `/v{snapshot}/sparql`; `metadata_file` is still projected for `sal query --info snapshots` but the UI no longer shows it); `push` puts the current snapshot's message at the end of the artifact's `org.opencontainers.image.description`.
    - All input RDF data should be validated. This RDF data can be defined in either Turtle or JSON-LD. 
    - For all input RDF data, if there is a term that is not defined in the provided prefixes, SAL will throw an error which calls out the specific line number with the offending term.
        - For instance, if the user makes a typo and specifies `schema:nameee` in their JSON-LD, SAL build will throw an error saying that `nameee` is not a defined term in the RDF vocab. This should be supported for any generalized RDF vocabulary.
    - Only new data should be written to the iceberg table. For instance, if the table already has a particular triple, it should be ommitted from the new commit. 
        - **A build's memory must not grow with the data.** An Iceberg build commits from a `load.Spool`, not from a graph: Parquet files of table rows (`triple_hash` included) in a scratch directory, `.sal/data/.scratch` (`load.ScratchDir`, cleared at the start of every build by `newBuildSpool` and removed when it ends). What module tasks produce is handed to `Spool.Add` as it is parsed; the graph of everything else (sources, imports, provenance) joins with `Spool.AddGraph` once its blank nodes are stabilized, and the triples `CONSTRUCT` queries produce join last. Never collect module output in the build graph or in a Go map or slice keyed per triple; that is what got a Geoconnex build OOM-killed at 32 GiB.
        - The diff against the table is DuckDB's, not Go's (`build/load/diff.go`, `spoolDiff`). `dumpExisting` writes the table's live `(triple_hash, predicate)` pairs to Parquet. The spool writes its files per partition of the table (`partitionKey`, the first 20 characters of the predicate, the table's truncate transform), and `spoolDiff.diff` first computes the pairs to delete over every spooled hash (`removed`: the existing pairs anti-joined with the spool, sorted by predicate then hash so the equality delete writer, which keeps a writer per partition, fills one at a time), then works one spool partition at a time: `added` anti-joins its rows with the existing pairs of its predicates and with the hashes earlier rounds added (`addedHashes`, which is how a staged build's commit excludes the staged rows once their spool files are gone), sorted by predicate, subject, then hash, which is the table's declared sort order and gives each row group of a predicate its own subject range, so a subject lookup or a join on a few subjects prunes to about one row group per predicate; the data files are written, and the partition's spool files dropped (`Spool.Drop`). Only one partition is ever sorted and the spool shrinks as the table grows, which keeps the disk a build needs near the spool's size; one global sort needed three to four times it and ran a 70-million-triple Geoconnex build out of disk. Both are anti joins and sorts, which DuckDB spills; a `DISTINCT` over whole rows does not spill and fails once the rows exceed `memory_limit`, so duplicates in the spool (a module writing a node twice, a source triple a module repeats) are dropped by `distinctRows` while the sorted rows stream into the writer: equal hashes are adjacent since copies of a triple share its predicate and subject. `writeRowFiles` writes the added rows with iceberg-go's clustered writer (`table.WithClusteredWrite`), which holds one partition open at a time because the rows arrive sorted by predicate; `asSchemaColumn` gives the WKB blob DuckDB writes back its geoarrow type, and the hash blob its fixed width. `applyWriteProperties` sets `write.parquet.row-group-limit` to 122880 rows, since iceberg-go buffers a whole row group and its default of a million rows of geometries is gigabytes.
        - The diff's DuckDB is a database of its own (`scratchDB`), not `query/sparql`'s shared handle: it reads and writes only Parquet, so it needs no extension downloaded and runs in unit tests, and it carries the build's settings (`memory_limit` from `pkg.DuckDBMemoryLimit`, `temp_directory` under the scratch directory, `preserve_insertion_order = false`, and one thread per 256 MiB of its limit, since a sort with a dozen threads and 512 MiB runs out of memory where two threads spill). It is opened for a round of statements and closed before Go writes the data files, which gives DuckDB's memory back first.
        - Reading the whole table goes through `load.ScanLiveRows`/`liveFiles.liveRowsSQL`, which list the current snapshot's data and equality delete files from the manifests and have DuckDB apply the deletes by sequence number (a delete removes a hash from files with a lower data sequence number, so a triple deleted by one build and added back by a later one is live). iceberg-go's scan holds every equality delete of the table in memory, which after a rebuild that removed millions of rows costs gigabytes; it is only the fallback for a snapshot carrying position deletes or deletion vectors, which sal never writes. `dumpExisting` and the STAC row count and extent both read the table this way.
        - `load.tripleDigest` is the 32 bytes of a row's SHA-256, computed by `digestTriple`, and the `triple_hash` column holds those bytes as an Iceberg `fixed[32]` (Arrow `FixedSizeBinary(32)`, Parquet `FIXED_LEN_BYTE_ARRAY`, DuckDB `BLOB`), not their hex, since the hex string was the largest column of the table. `columnWriteProperties` turns dictionary encoding off for it, for `object_geometry`, and for the numeric and time columns (`object_byte`, `object_integer`, `object_float`, `object_time`), and writes a Parquet bloom filter on `subject` and `object_iri`, which DuckDB's `iceberg_scan` probes for a constant equality filter and skips a row group on. iceberg-go gives arrow-go no distinct value estimate, so every filter is written at its maximum size, `bloomFilterMaxBytes` (128 KiB, set through `write.parquet.bloom-filter-max-bytes`, whose default of 1 MiB per column per row group would outweigh most files); sizing them to the row group needs iceberg-go to pass an NDV or enable arrow-go's adaptive filters. DuckDB writes the column back from the diff as a variable length blob, which `asSchemaColumn` copies into the fixed width type. `NewIcebergTableFromCfg` refuses a table whose `triple_hash` is still a string and tells the user to `sal clean --wipe` and rebuild.
        - `pkg.Budget` is how much memory sal plans for: `SAL_MEMORY_LIMIT` when set, else the cgroup limit (`automemlimit`'s `memlimit.FromCgroup`, which is what a container is killed at), else physical memory. `main` calls `pkg.ApplyGoMemoryLimit`, which sets the Go soft limit to 70% of it unless `GOMEMLIMIT` is set, and the diff's DuckDB gets 50%; the shares overlap because module parsing and the DuckDB diff do not run at once. `BuildCmd.Run` logs the budget. Nobody should have to set a memory flag for a build to fit; prefer making a step stream over adding one.
        - An identifier for each triple can be calculated by hashing the subject, predicate, object, the object's datatype (empty for an IRI or blank node object), and the object's language tag (empty for anything but an `rdf:langString`). This hash identifier can then be looked up in the iceberg table to check if it exists. The datatype and language are part of the identity because the table records them in `object_type` and `object_language`, so two literals with the same lexical form but different datatypes or language tags are distinct rows.
    - Build also materializes triples from every sal module task the project declares and adds them to the iceberg table, in the same snapshot as the sources. A build is the one operation that produces a snapshot, so `sal run` is only a debugging command: it re-runs the tasks on top of the last build through the same `BuildCmd.Run`, after checking that the table's current snapshot was built from HEAD, and warns on every start that it is for debugging. `--without-sal-modules` (`BuildCmd.WithoutSalModules`) makes a build commit only the task configuration, validated against the module ontology like any other RDF, without invoking any run command. A project declaring no task builds cleanly either way; only `sal run` fails with `ErrNoModuleTasks` when there is nothing to run, which `BuildCmd.fromRunCmd` is what tells it.
        - A sal module is another github repository with a Dockerfile in the root. 
            - More info on the sal module spec can be found here: @./docs/src/content/docs/reference/salmodule-description.mdx
            - An example sal module can be found here: @./examples/salmodule/python-geoconnex
        - A sal module is referred to in an rdf file by using the sal module ontology here: `https://w3id.org/sal/salmodule#`
        - If a new term is defined in the sal module that is a subclass of `salmodule:Task` the sal module should be built by fetching the remote git repository, building the docker container, and running it with the task instance passed through the `SALMODULE_TASK_INSTANCE` environment variable (`salmodule.TaskInstanceEnvVar`, the name the ontology's `salmodule:TaskInstance` individual fixes). The JSON-LD that results from this process should be added to the in memory goRDFlib graph and thus added to the iceberg table upon a successful build. 
        - `salmodule:Task` is the only task class a module subclasses. `salmodule:NodeProducer`, `salmodule:NodeConsumer`, and `salmodule:NodeProcessor` are defined in `specs/salmodule.ttl` by OWL axiom as a `Task` whose class carries a `salmodule:stdoutShape`, a `stdinShape`, or both: they are what a reasoner infers from the shapes, never what decides sal's behavior. sal reads every task's stdout and validates it when the class declares a `stdoutShape`; a class without one is run unchecked with a warning, since declaring what a task produces is part of the module contract but older modules predate the shape. A module class that subclasses one of the inferred classes directly, or a project instance typed with one, is still recognized as a task (`salmodule.IsTaskBaseClass`) so those modules keep working, but `parseModuleOntology` and `findSalModuleTasks` warn and point at `salmodule:Task` (`salmodule.IsInferredTaskClass` is what tells the two apart). `specs/salmodule-ontology.schema.json` is stricter than sal here on purpose and accepts only `salmodule:Task` as a parent, since it is the editor's guide to writing a module.
        - A task instance is configured in RDF, not with an embedded JSON-LD literal. `salmodule.ModuleOntology.TaskInstance` serializes the instance into the JSON-LD node object the module receives: every property of the instance whose predicate is in the module's own namespace becomes a key, and IRIs are written the way the module's ontology writes them (a module term becomes its relative name, any other IRI is shortened with a prefix the ontology's `@context` binds). An RDF list object (`( ... )` in Turtle; `isList` checks for `rdf:first` or `rdf:nil`) becomes a JSON array in list order via `rdflibgo.NewCollection`, which is what a module's `@container: @list` term expects; a repeated property becomes an array sorted by encoding since RDF gives it no order.
            - The serialized JSON-LD node object is what the `salmodule:RunCommand` individual of `specs/salmodule.ttl` documents; it is the input the run command is invoked with. The command line itself is fixed by the `salmodule:SALModuleCommand`, `OntologyCommand`, `RunCommand`, and `TaskInstance` individuals, whose `rdfs:label` is the word on the command line or the variable's name, and mirrored by the constants in `salmodule/module_ref.go`; the ontology has no `baseCommand`, `ontologyCommand`, or `runCommand` property any more, and the JSON schema refuses those keys. The variable's name cannot be changed by a module: the `salmodule:taskInstanceEnvVar` property that once allowed that is gone from the ontology (which now has no `owl:OntologyProperty` at all; `protocolScheme` is an `owl:AnnotationProperty`), the JSON schema refuses the key, and a project writing it gets an undefined term error from validation.
        - An example project using a salmodule might look like @./build/testdata/reference/ontology_with_sal.ttl 
        - An instance is only run when it is known to be a task. Either the project's RDF types it as a `salmodule:Task` (or, with a warning, one of the inferred classes), or the module's own ontology declares its class as a subclass of `salmodule:Task`. A `salmodule://` typed instance that is neither is left alone, with a warning. What is never left alone is a module whose ontology could not have a task: `Resolver.Ontology` runs `ModuleOntology.requireTaskClass` on every document it parses, which refuses one whose `@context` binds the `salmodule` prefix to anything but `salmodule.Namespace` (every `rdfs:subClassOf salmodule:Task` in it then names a class sal does not know, which is how a project once built a module's tasks as nothing at all) and one that declares no subclass of `salmodule:Task`, which the specification requires. `sal validate --salmodule` does not run that check, since the JSON schema already reports both on their own lines. `materializeTask` also warns about a task that ran and produced no triples and no files, since a task that exits cleanly having written nothing is usually misconfigured.
        - A task writes newline delimited JSON, not JSON-LD, to stdout. The module ontology's `@context` must be injected into each node before it is converted to RDF, since it is what resolves the task output's keys to the module's vocabulary.
        - A task's output is parsed as it is written, never held whole. `Resolver.RunTask` hands each non-empty line of stdout to a `salmodule.TaskOutputSink` as it reads it, and `ModuleOntology.NewTaskOutputParser` returns the `TaskOutputParser` whose `Line` is that sink for a build: it gathers lines into a batch (`taskOutputBatchLines` lines or `taskOutputBatchBytes` bytes, whichever first), parses the batch as one JSON-LD document with the module `@context` injected, and hands each triple to a `salmodule.TripleSink`: `ModuleOntology.NewTaskOutputStream` takes the sink, which for an Iceberg build is `load.Spool.Add`, so the output goes to disk as it is parsed and no graph of it is ever built; `NewTaskOutputParser` adds to a graph instead, which `MaterializeSalModules` does when it is given no sink (an N-Quads build, which serializes a graph). A batch's blank nodes are labelled one connected component at a time by `pkg.StableBlankNodeComponents`, from a digest of the whole component (every triple, IRIs and literals included) plus the refinement's label within it, so a node's labels depend on that node alone and not on its batch or on anything else the build holds: a blank node is local to the line that writes it, and two components alike in every triple get the same labels and are one set of rows. Deriving them from the refinement alone is wrong: it stops once a pass splits nothing, so every lone blank node keeps the signature it started with and they all collide. The parser records the subjects typed `salmodule:Error` and keeps their own triples in a scratch graph, and holds back the triples naming a `file:///` IRI, which it never hands to the sink; `Finish`, called after the task has ended whether or not it succeeded, parses what is still pending and reports the error nodes as a `TaskError`. A line that is not a JSON object stops the task through the sink's error, like a shape violation does. A failed task leaves what it wrote so far in the spool, which the failed build discards. `materializeTask` counts what a task materialized as the triples handed to the sink, and the JSON-LD documents (lines) it read; every `documentsProgressStep` (20,000) documents it sets `sal.module.documents` and `sal.triples.materialized` on the running `salmodule.task` span, which the progress pane shows once past 20,000, and logs the count.
        - stderr is a task's control channel, not its data, and is read as it is written too. `ContainerRunner.RunContainer` hands the consumer a `ContainerOutput` with both streams (the daemon's multiplexed attach stream is demuxed into a pipe per stream, so a consumer must drain both; `dockerRunner` creates the container with the `none` logging driver and attaches before starting it rather than following its logs, since a logging driver keeps everything the task writes on the daemon's disk however fast sal reads it, which on a Cloud Run job's in-memory filesystem is memory, and a harvest writing faster than sal parses ran a 32 GiB job out of it; an attached stream holds nothing and blocks the task's writes until sal reads them, so `docker logs` shows nothing for a module container; `dockerRunner` also keeps a bounded `stderrTail` for the error a non-zero exit is reported with). `RunTask` takes a `TaskStream` (validator plus sink) per stream, reads both through one channel of `streamLine`s on one goroutine so no sink or validator runs concurrently, and routes each stderr line through `handleStderrLine`: a line that is a JSON object goes through the stderr validator and sink with its line number on that stream, anything else is a log line logged as a warning and otherwise dropped. `ModuleOntology.NewTaskStderrParser` is the sink for a build: the same `TaskOutputParser` over a scratch graph, so nothing on stderr reaches the build graph, whose `Finish` reports the `salmodule:Error` nodes as a `TaskError`. The spec has errors on stderr; `TaskOutputParser.Finish` still reports an error node found on stdout, with a warning, since a module written before that was settled puts it there. `materializeTask` finishes the stderr parser first and reports a `StreamShapeError` ahead of either parser's `TaskError`, and either `TaskError` ahead of the container's exit status.
        - A relative IRI in a task's output resolves against the project base, never against the module's namespace. `NewTaskOutputParser` takes the base explicitly and `MaterializeSalModules` passes the base of the graph being built, which is `pkg.DefaultSalBase()`. What a task produces is instance data owned by the project that configured and ran it; the module's namespace names its vocabulary. A module that wants its output under another namespace writes absolute IRIs, which are kept as written.
        - A task that reports `salmodule:Error` nodes, on stderr where the specification puts them or on stdout, fails the build with the messages the module reported. An error node must carry both an `rdfs:label` and an `rdfs:comment`, as the `stderrShape` on `salmodule:Task` in the spec requires, and `TaskOutputParser.Finish` reports each node as `label: comment` (`errorNodeMessage`). That requirement is enforced by the parser rather than by running the spec's shape through `StderrValidator`, which would stop the task at the first malformed node and hide its report: a node missing either property still fails the build, with a message that carries what the node did say and names what it lacks. The `salmodule` skill, `edit.AgentPrompt`, the example module, and the integration fixture all write both.
        - The vocabularies a task's output is stated in are pinned like the ones the sources declare, since their terms reach the table all the same. `TaskOutputParser` records, as it parses each batch, every predicate, every class a node is typed with, and every literal datatype the output used (`terms`), and separately every namespace a `@context` binds (`bindings`): the module ontology's context, read once when the parser is made, and the `@context` any line carries, at its top or on a nested node, decoded only for a line that contains `@context` (`noteContexts`/`noteBindings`: a prefix or `@vocab` value as it is, the `salmodule.VocabularyNamespace` of an expanded term definition's `@id`, and a scoped context's bindings; a keyword alias binds nothing and a remote context is not fetched). `Vocabularies` reports, for each used term, the longest binding it starts with, the way `longestPrefixBase` finds a source file's declared prefix. A term the output only wrote as a full IRI is parsed like any other but pins nothing: a full IRI is a reference, the way one in a Turtle file is, while a bound prefix declares that the output is stated in that vocabulary, which is what keeps a harvested Geoconnex node typed with a KnowWhereGraph S2 cell class from pinning that ontology. A namespace that only names subjects or objects is instance data, not vocabulary, and a prefix the module's `@context` binds without the output using it (`sh` for its shapes, say) is never among them. The `salmodule` skill and `edit.AgentPrompt` tell a module author to bind a prefix for every vocabulary the output uses, under the prefix the output writes it with. `MaterializeSalModules` merges them across tasks and `build.go` hands them to `validator.PinMaterializedVocabularies`, which resolves and pins each one through the same `vocabularyCache.load` a declared prefix goes through, but only warns about one it cannot resolve, since module output is never validated against its vocabularies and a module may state triples in a namespace no document is served for; the project base, xsd, and anything that is not an `http`, `https`, or `salmodule://` IRI are passed over silently. This is why `pins.Save` and `pins.AppendProvenance` run after module materialization rather than before it.
        - A task class's `salmodule:stdoutShape` is enforced, line by line, as the task writes, and its `salmodule:stderrShape` the same way over the nodes on stderr. `ModuleOntology.StdoutValidator` and `StderrValidator` build a `salmodule.StreamValidator` from every `stdoutShape`, respectively `stderrShape`, the class, or a superclass the module ontology declares for it, carries, and return nil when there is none so a module without one pays nothing; the usual module declares no `stderrShape`, since the spec's `salmodule:Task` already says what an error carries. `collectShape` copies only the shape's closure into the shapes graph (never following the `stdoutShape`/`stderrShape`/`stdinShape`/`taskShape` annotations themselves), so the ontology's other shapes never apply to a stream. A shape using `sh:languageIn`, `sh:uniqueLang`, `sh:disjoint`, `sh:qualifiedValueShapesDisjoint`, or `sh:sparql` is refused when the validator is built. `Resolver.RunTask` takes each stream's validator in its `TaskStream` and calls `ValidateLine` on each node before any `file:///` it names is copied or the sink sees it; the line is parsed with the module `@context` injected and the project base, exactly as `TaskOutputParser` will parse it, and validated with goRDFlib's `shacl` package. The first `sh:Violation` returns a `StreamShapeError` naming the stream (results of lesser severity are logged), which cancels the copies in flight and makes `ContainerRunner.RunContainer` kill the container: a consumer error would otherwise leave the attach stream, and so the demuxer, blocked until the task exited on its own. `MaterializeSalModules` reports a `StreamShapeError` ahead of any `salmodule:Error` the partial output holds.
        - A task can hand over files as well as triples. Any IRI in its output with the `file:///` scheme names a file inside the container, and `salmodule.Resolver.RunTask` copies it out into `.sal/data/blobs` under the SHA-256 digest of its contents while the task is still writing: `ContainerRunner.RunContainer` streams the container's stdout to a `ContainerOutputConsumer` together with a `ContainerFiles` handle over the daemon's copy endpoint (what `docker cp` uses), and keeps the container until the consumer returns, so a copy may finish after the task has exited. `salmodule.fileCopier` scans each line that contains `file:///` as it arrives (a line without the prefix is not decoded at all), starts a goroutine per distinct path, hashes into a temp file, and renames to the digest only once complete; a repeated path is warned about and skipped; `wait` blocks on every copy before `RunTask` returns its `TaskResult`. The scan looks at every string value on the line, since key coercion is only known once the module's `@context` is applied, so a `file:///` literal is copied on sight and then discarded with a warning by `LinkCopiedFiles`.
        - A `file:///` IRI ending in a slash names a directory (`containerFilePath` reports the trailing slash as `isDir`), which is for output only useful whole, a Zarr store or a STAC catalog whose `href`s name its neighbours. `ContainerFiles.CopyDirectory` walks the daemon's tar of the directory (`walkDirectoryArchive` strips the base name the daemon prefixes and refuses a file, a link, or anything else that is not a regular file or directory), and `fileCopier.copyDirectory` unpacks it into a `.copying-*` temp directory and then renames it to `.sal/data/blobs/<treeDigest>/` once the digest is known, replacing whatever an earlier copy of the same contents left there. Everything in the blob store but `prov.jsonld` is named by a bare hash. The files inside are kept verbatim, never renamed, so the directory works in place from disk, from `/blobs/<digest>/`, or from a bucket `upload` copied `.sal/data` to, with no rewriting or lookup; naming the directory by digest rather than by its container path is what keeps two modules that both write `/out/catalog/` from colliding. The digest is `treeDigest`, the SHA-256 of one line per regular file sorted by relative path (`path\0<file sha256 hex>\n`), so it ignores mtimes and tar order, and `CopiedFile.Directory`/`BlobPath` carry the kind and the path relative to the blob store (`<digest>` for a file, `<digest>/` for a directory). `CopiedFile.Source` is the module IRI the copy is attributed to, set by `RunTask` from the module namespace without its trailing slash, the same IRI `Resolver.Downloaded()` records the module under.
        - `salmodule/prov.go` owns `.sal/data/blobs/prov.jsonld`, an append-only log of every file and directory a task has copied into the blob store, in the shape `.sal/config.jsonld` records a pinned vocabulary in: the node's `@id` and `owl:versionIRI` are both `urn:sha256:<digest>`, the IRI the graph refers to the copy by, so two modules producing the same container path never share a record; `rdfs:label` is the `file:///` IRI the task named it with (`CopiedFile.FileIRI`); `dcterms:identifier` is its blob-relative path (`provNode.blobPath`, falling back to the bare digest of the `@id` for a record without one); `dcterms:source` is the module IRI (`CopiedFile.Source`); plus `dcterms:modified` and `rdfs:comment`. `Provenance.AppendProvenance` carries those records into the graph on every `build` (`build.appendBlobProvenance`), so a table rebuilt from source still describes every copy the blob store holds. `recordCopies` is called from `LinkCopiedFiles` for every copy that is kept, file or directory, replacing only a node with the same `@id` (the same contents copied again) and leaving everything else in the file alone. Nothing prunes the log or the blob store during a run: a directory an earlier run copied that this run did not produce stays on disk and in `prov.jsonld`, and clearing it is the user's job. `RemoveCopiedFiles` is the wipe-time counterpart that removes every recorded copy and the file, the one place sal removes a copy. `serve` needs no lookup to find a copy, since a directory sits under its digest like a file does; `Provenance.Label` is how `serve.serveZip` names the archive after the task's `file:///` IRI rather than the digest.
        - `salmodule.LinkCopiedFilesTo` runs in `MaterializeSalModules` once the task has ended and hands its triples to the same sink the output went to (`LinkCopiedFiles` is the form that rewrites a graph in place), over the triples `TaskOutputParser.FileTriples` held back rather than a scan of the build graph, which holds far more than the task's output and whose own `file:` IRIs are none of the module's business: every `file:` IRI in them, as subject or as object, becomes `urn:sha256:<digest>`, the same form pinned vocabulary documents are named with so `serve` answers `/blobs/{digest}` for a copy too, and the copy is described the way a pinned vocabulary's provenance node is: `rdfs:label` (the `file:///` IRI the task wrote, ending in a slash for a directory), `dcterms:modified` (the tar header's mtime from the container, the newest one for a directory, falling back to the copy time), `owl:versionIRI` (the digest IRI itself), plus `dcterms:identifier` (`BlobPath`, where it sits under the blob store) so a service reading the table can form the copy's location from a blob store root. Whatever else the task said about the `file:///` IRI as a subject travels with it, which is how a module attaches its own metadata to a directory. A subject occurrence counts as a reference, so such a copy is kept. A `file://` IRI with a host or one that was not copied is an error. `MaterializeSalModules` logs how many files each task copied.
        - `serve.blobHandler` serves a hash name as before (the file under that name, or the directory under it zipped on the fly with `archive/zip`), and any other path as a file under `.sal/data/blobs` with a content type from its extension, or as a zip when it is a directory; the path is confined to the blob store with `path.Clean` and `fs.ValidPath`. With `--with-ui`, `/blobs/{blob...}` is routed straight to the API and only `/blobs` and `/blobs/` go through `browserRoute`, so a browser following a link into a copied catalog gets the file and not the tab.
        - Materialization happens in `build` only, after validation and after the uncommitted changes check, so that nothing is run for a build that would be rejected anyway.
    - Build pins the exact version of every vocabulary the project resolves against. See the `validate` section below for the store; `build` is what fills and writes it.
        - `build.projectVocabularies` opens `.sal/config.jsonld` for the project being built, or an ephemeral store when there is no SAL project to pin for. `--no-cache` sets `Refresh`, which resolves everything from source again and re-pins it.
        - `validator.PinDeclaredPrefixes` runs after the validation loop and resolves every prefix the source files declared, not only the ones a term was used from. A declared prefix that cannot be resolved fails the run.
        - `pins.Save` is called only after the uncommitted changes check and after module materialization, which pins the vocabularies the tasks' output uses. `.sal/config.jsonld` is a git tracked file, so writing it before that check would leave the worktree dirty and make the next build refuse to run. `Save` is a no-op when nothing changed, which keeps a repeat build clean. It preserves the project node the file already carries, since pins never inspects it.
        - `pins.AppendProvenance` runs right after `Save` and adds an `owl:Ontology` node with the same `rdfs:label`, `owl:versionIRI`, `dcterms:format`, `dcterms:modified`, and `rdfs:comment` the config file records for every pinned vocabulary directly into the graph being built, so which exact version a build validated against is queryable in the triples table itself, not only recorded in `.sal/config.jsonld`. It runs after `NewTermsHaveClassDefinitions`, so this provenance is not subject to the project's own RDFS checks, the same way imported and module-materialized statements are not.
    - Build also merges in the ontologies the project imports. `build.ImportOntologies` reads the `owl:imports` IRIs out of the project node in `.sal/config.jsonld` and resolves each one with `validate.PinnedGraph`, so that an imported ontology is carried by the data product at the version the project pinned rather than only referenced from it, as the project's own statements.
    - Importing is the only way a vocabulary's statements reach the table. A vocabulary the project pins but does not import is validated against and recorded as provenance, and nothing else: there is no column marking rows as a vocabulary's, and the table holds only what the project asserts, imports, materializes, or records as provenance. One release wrote every pinned vocabulary into a `vocabulary` column instead; `NewIcebergTableFromCfg` refuses a table that still has that column and tells the user to `sal clean --wipe` and rebuild, the same as a table older than `object_language`.
        - The project ontology's own statements do not arrive this way. The project node has no file of its own for the walk that collects source files to find, since `.sal` is skipped entirely and the node shares a file with pins. `build.projectOntologyContent` instead renders the node as a standalone JSON-LD document with `importation.SerializeOntology`, and `build.go`'s `Run` parses it directly with `validator.ParseContent` and folds its bytes into the source hash with `pkg.HashFilesAndContent`, so it is still validated, counted, and hashed like any other source file even though it is not one.
        - Fetching the imports happens in `build` only, in the same place as module materialization: after validation and after the uncommitted changes check. `validate` never fetches imports.
        - Imports are fetched with the same content negotiation and format sniffing a vocabulary lookup uses, but they are not cached; only vocabulary term sets are.
        - Not every import is an ontology document. An `oci://` import is pulled to `.sal/data/imports` and `dropImportStatement` takes its `owl:imports` statement back out of the graph, so nothing about the artifact reaches the table. A `salmodule://` import is a document like an `http` one, except that `validate.PinnedGraph` obtains it by cloning and building the module; its statements are merged like any other import's, and the module joins the ones `Resolver.Downloaded()` records in the table.
        - The imported statements are added after `NewTermsHaveClassDefinitions` has run, so an imported ontology is not subject to the project's own RDFS checks.
    - Build runs every SPARQL CONSTRUCT query in the project's `sparql/` directory over everything it has gathered and commits what they construct in the same snapshot as the sources and the module output. See the `construct` section below for the queries themselves; this is what is specific to a build.
        - **A build commits exactly one snapshot to the main branch, and main never points at a snapshot holding the sources without what is constructed from them.** `build.MaterializeConstructs` runs after `appendBlobProvenance` and before `ExportGraph`. The queries are answered by the SPARQL to SQL translation, which reads a table, so `stageGraph` stages the build's spool with `load.StageSpool` on the `sal-staging` branch (`load.StagingBranch`) of the project's own table and returns a `DuckDBRunner` with `SnapshotID` set to the staged snapshot. Staging writes only the diff against main, never a copy of the table: data files for the triples the table lacks and equality deletes for the ones it should no longer hold, which include what the last build constructed. Staging `Mark`s the spool, and the constructed triples are spooled into the next segment; `ExportGraph` then commits through `StagedGraph.Commit`, which keeps the staged data files as they are and diffs only the new segment, against the table and the staged rows, in the same `spoolDiff` (kept open so the table's hashes are read once): what neither holds is written, and a row the staging deleted that the segment holds again is kept, so a rebuild of unchanged sources still commits nothing. The snapshot's parent is the last build's and its summary is the whole change. `BuildCmd.Run` defers `StagedGraph.Discard`, which removes the branch, the staged snapshot, and every file only that snapshot refers to (`removeStagingBranch` calls the `PostCommit` of iceberg-go's remove snapshots update by hand, since a catalog commit does not run it), and drops a table that staging created when nothing was committed to it. Never commit the sources to main first and the constructed triples second: that would leave a snapshot a rollback could land on. `TestBuildStagesOnABranchAndCommitsOneSnapshot`, `TestEveryBuildWithConstructQueriesAddsOneSnapshot`, `TestBuildCommitsNothingWhenAConstructQueryFails`, and `TestAFailedConstructQueryLeavesTheLastBuildAsItWas` run the real staging write and guard this; keep them passing rather than faking `stageGraph` away in them.
        - A build killed between staging and discarding leaves the branch behind. Main is untouched by it, and `load.StageGraph` removes a branch it finds before making its own. `removeStagingBranch` never removes a snapshot another branch or tag still reaches, since the branch points at main's head for the moment between being created and being committed to.
        - A format other than Iceberg has no project table to stage in, so `stageGraph` writes the whole graph to a temporary warehouse (`os.MkdirTemp`, namespace `staged`) for it and removes it once the queries have run.
        - A project with no CONSTRUCT query stages nothing, so it pays nothing for the step; `MaterializeConstructs` still calls `construct.Run` with no queries so that `.sal/constructed` is wiped of what an earlier build wrote.
        - `load.StabilizeBlankNodes` (over `pkg.StableBlankNodeIDs`) rewrites the graph it is given in place and returns it: only the triples touching a blank node are taken out and put back under their `sal_<hash>` labels, and the signatures are refined over an index of those triples by blank node, so a graph of millions of triples is never copied to stabilize it and the cost is the blank node triples, not the blank nodes times the graph. The refinement stops once a pass no longer splits a class of equally signed blank nodes, never once the signatures themselves repeat: a blank node that leads to another gets a new signature every pass, so waiting for them to repeat costs a pass per blank node in a cycle, each over every blank node triple, which is what made a build hang on a module output with tens of thousands of nested blank nodes. `build.go` stabilizes the graph once, before it joins the spool, and nothing is renamed after that: the staged snapshot names blank nodes by their `sal_<hash>` labels, a constructed triple about a blank node refers to it by that label, and the commit keeps it, so the labels in `.sal/constructed` are the table's and the staged data files are always committed as they are. `MaterializeConstructs` returns the constructed graph, which `build.go` spools and merges into the graph it returns.
        - Every query reads the graph as it stood before any of them ran. A query never sees what another constructed, so the order they run in cannot change the result, and a rebuild of unchanged sources constructs the same triples and commits nothing.
        - `construct.FindQueries` is called before validation, next to the source hash, so that a query sal cannot parse or translate fails the build before any vocabulary is fetched or module run, and so that the query files are folded into `sal.hash` with `pkg.HashFilesAndContent`. It is skipped for `sal validate` (`skipCommit`), which runs no query.
        - Constructed triples are added after `NewTermsHaveClassDefinitions` and are not checked against the project's vocabularies, the same as imported and module-materialized statements.
        - Tests replace `stageGraph` to keep DuckDB, whose Iceberg extension has to be downloaded, out of a unit test. A test about snapshots wraps the original instead (`installRealStaging`), so the build is still staged on the branch and only the runner is a fake.
    - The last step of an iceberg build is `build.WriteProjectStacCatalog`, which writes a STAC catalog to `.sal/data/stac` from the committed table: `catalog.json` and `triples/collection.json`, the collection carrying the STAC Iceberg extension (`https://portolan-sdi.github.io/stac-iceberg-extension/v1.0.0/schema.json`) alongside the Table and Projection extensions. Everything is read from the table after it is written, not from the in-memory graph: the metadata location, snapshot, format version, partition spec, and columns from the metadata, and the row count and spatial extent from one scan of `object_geometry` through `load.ScanLiveRows` (the summary's `total-records` does not subtract equality deletes, so the scan is what keeps the count exact, and DuckDB applying the deletes is what keeps it from costing the table's deletes in memory). The directory is rewritten whole on every build and sits under `.sal/data`, not beside `.sal/config.jsonld`, because it names the current metadata file and would otherwise dirty the worktree after each build. `serve` serves it at `/stac/` and `clean --wipe` removes it. `push` and `upload` carry the directory as-is, so an uploaded copy still points at the local `file://` metadata path; rewriting it for a bucket is not done. `moduleStacCatalogs` then walks `.sal/data/blobs` for directories a module task handed over whose `catalog.json` is a STAC Catalog or Collection and appends a `child` link to each in `catalog.json`, by a path relative to the stac directory (`../blobs/<digest>/catalog.json`), so the module's catalog and sal's are one tree wherever `.sal/data` sits; since a run never removes earlier copies, every version of a module's catalog still on disk is linked; the module's files are not copied or rewritten, since their own links are relative to where they are, and a catalog inside a linked one is skipped since it is that catalog's to list.

### `construct`

- Runs every SPARQL CONSTRUCT query in the project's `sparql/` directory against the built triples table and writes the graph each one builds to `.sal/constructed/<name>.ttl`. It is a debugging command, and warns that it is one on every start: it only reads the table, and never writes to it or creates a snapshot. `sal build` is what commits constructed triples; see the `build` section above.
- `construct.FindQueries` walks `sparql/` recursively. A file is a query when it ends in `.rq` or `.sparql`; a query that is not a CONSTRUCT is skipped, and one that does not parse or that `salsparql.ToSQL` cannot translate is an error naming the file. `Query.Name` is the path under `sparql/` without its extension, which names the output file, so two files differing only in extension are refused.
- `construct.Run` is the one function both `sal construct` and `build.MaterializeConstructs` call. It removes `.sal/constructed` before anything else, so the directory never holds the output of a query that was renamed or removed, and with no queries it only removes it. It returns the graphs of every query merged into one, which `build` adds to the graph it commits and `sal construct` discards.
- The output is Turtle, not JSON-LD: it is the smaller file and needs no `@context` resolved to write or read. It is written with the prefixes the query itself declares (`salsparql.ConstructPrefixes`, carried on `Query.Prefixes`).
- `.sal/constructed` must be gitignored, and nothing a build does may change a tracked file, since that would leave the worktree dirty for the next build. `sal init` adds the entry to `.gitignore`; for a project whose `.gitignore` does not cover it, `ignoreInGit` asks `git check-ignore` and writes a `.gitignore` holding `*` inside `.sal/constructed` itself rather than editing the project's.
- `construct.Runner` is the one method `Run` needs, `Construct(ctx, query, rowFn)`, which `salsparql.DuckDBRunner` implements and tests fake. A row is read back into RDF terms with `export.SubjectTerm` and `export.ObjectTerm`, the same functions `sal export` rebuilds the rows of the table with. Do not write a second row to term conversion.
- `sal construct` reads the table the last build committed, which already holds what the queries constructed then. A query whose pattern matches its own output constructs more there than it did in the build, which ran it before those triples existed. That is expected, and is documented for the user.
- `sal clean --wipe` removes `.sal/constructed` with the data product.

### `import`

- Records an external ontology on the project node of `.sal/config.jsonld`, which `build` reads its `owl:imports` from. `sal import` creates the file if it does not exist, and creates the node if the file already exists only because a build has pinned vocabularies into it.
- The node names the project itself as `"@id": "."`, which resolves against `pkg.DefaultSalBase()`, the same base the project's own relative terms resolve against. It is one node typed by what has been recorded on it: `sal init` writes it as a `schema:Project` carrying `dcterms:description`, and the first `sal import` adds `owl:Ontology`, the title, the imports, and the comment to the same node, keeping the description (`"@type"` is a string for one type and an array for both). `importation.Ontology.IsProject` and `IsOntology` are read from the node's types and written back as they were, so a rewrite never adds a type the node did not have; `sal init` sets `IsProject` and `sal import` sets `IsOntology`. `dcterms:title` is the git project name (`pkg.GitProjectName`, the last segment of the remote URL), which `sal init` records and `sal import --title` replaces; sal writes Dublin Core Terms (`dcterms:`) everywhere it writes a title, creator, description, or date, in the project node, a module's scaffolded `ontology.jsonld`, `salmodule/sal_ontology.jsonld`, and `specs/salmodule.ttl` (which binds the terms namespace under the label `dct:`), and never the elements vocabulary (`dc:`); `ReadOntology` still reads a `dc:title` written before the node used dcterms and `SerializeOntology` writes it back as `dcterms:title`. `rdfs:comment` is always generated fresh, naming the git project, and is not user configurable. `serve`'s stats view reads `Title` and `Description` from the node, which is what the UI's landing card shows under the name and path.
- `importation` parses the node with `goRDFlib/jsonld.Parse` but renders it from a Go struct marshaled with `encoding/json`, so the generated shape stays flat and readable; `renderOntology` declares only the prefixes the node uses, since `build` validates that document like a source file and pins every prefix it declares (a project node pins `schema.org` and `dcterms`). A node carrying statements the struct does not cover is written back through `goRDFlib/jsonld.Serialize` instead, so hand written triples are never dropped. `importation.ReadOntology` and `WriteOntology` isolate the project's own node from the rest of `.sal/config.jsonld`'s `@graph` with `pkg.PartitionConfigGraph`/`SplitJSONLDDocument`/`JoinJSONLDDocument`, so the pinned vocabulary nodes `build/validate` owns never affect node parsing, extra-statement detection, or serialization, and `WriteOntology` re-reads the file and carries them forward untouched rather than overwriting the whole file.
- The file was Turtle headed by an autogenerated banner comment before it became JSON-LD; JSON has no comment syntax to carry that banner in, so the file no longer has one. The node is still regenerated on each import, so a hand edit still only survives when it is a statement the struct or the graph already carries.
- `importIRI` resolves what a reference was given as into the IRI recorded with `owl:imports`, and it accepts three kinds: an `http` or `https` URL, a `salmodule://` reference to a SAL module, and an `oci://` reference to an OCI artifact. A reference that names an artifact but omits the scheme is recognized by `looksLikeArtifactReference` so it can be reported as a missing `oci://` rather than as a malformed URL; anything else is reported as not a URL.
    - An `oci://` import is pulled to `.sal/data/imports` as it is recorded, so that an import missing from disk is restored rather than silently skipped, and `supersedeArtifactImport` drops the entry and the files of the version it replaces. It is the only kind dereferenced at import time; an `http` or `salmodule://` import is recorded and left for `build` to resolve.
    - A `salmodule://` import is an ontology document like an `http` one, so `build` merges its triples into the table; only where the document comes from differs. `validate.PinnedGraph` already dereferences the IRI by cloning and building the module, the same path a `salmodule://` vocabulary lookup takes.
    - A module is recorded under the IRI naming it, which is `ModuleRef.Namespace` without its trailing slash. Normalizing through `ParseModuleIRI` fills in the default host, so the same module written with and without it is recorded once; dropping the slash keeps a project that binds a prefix to the vocabulary base from having the `owl:imports` statement itself checked against the module's own terms. `PinnedGraph` parses the fetched document back against `Namespace`, for the same reason `vocabularyCache.parseBase` does.
- `.sal/config.jsonld` is a source file that belongs in git, and `build` treats the project node it carries as one, though the node has no file of its own; see `build.projectOntologyContent` in the `build` section above. `pkg.FindRdfDataInPaths` skips the `.sal` directory so that iceberg metadata under `.sal/data` is never mistaken for project RDF.
- `sal clean --wipe` removes `.sal/config.jsonld` along with the data product, so a wipe returns the project to the state it was in before anything was built or imported. It is removed even when there is no data product to delete, and `wipe`'s confirmation prompt names the file whenever it exists since it is a source file rather than a build artifact. The vocabulary documents the pins it carries name go the same way; `clean.removeProjectConfig` reads the pins to find them, since they sit under `.sal/data/blobs` rather than inside the table that a wipe removes wholesale. The files and directories module tasks handed over and `.sal/data/blobs/prov.jsonld` go too, through `clean.removeCopiedFiles`/`salmodule.RemoveCopiedFiles`, since they are artifacts of a run that the next run regenerates, and a wipe is the only time sal removes them.

### `validate`

- Validates RDF source files without committing anything. It runs the same pipeline as `build` with committing and sal project checks skipped, so any behavior described here applies to `build` as well.
- Every URI-backed term used in a file is checked against the vocabulary declared for its prefix. An undefined term is reported with the file, the line number, and the offending term.
- `validate.Validator` holds one `vocabularyCache` for a whole run, so a vocabulary is resolved once no matter how many files use it, and so `PinDeclaredPrefixes` can resolve every prefix the files declared once they have all been read. `ValidateRDFFile` is the single file wrapper around it.
- Declared prefixes are checked too, not only the terms used from them, and they are checked first: `build` parses every file with `Validator.ParseFile`/`ParseContent` before checking a single term with `Validator.Validate`, so the prefix checks and the prompt below run before any vocabulary is fetched. A vocabulary declared under namespaces that mix `http`/`https` or a trailing `/` or `#` is one error per vocabulary (`Validator.ConflictingPrefixes`, a `PrefixConflict` whose `Error` names every file and spelling); `build` logs each and returns the short `ErrConflictingPrefixes`. A namespace ending in neither `/` nor `#` is warned about and requires confirmation or `--allow-prefixes-without-slash-or-hash`; `Validator.PrefixesWithoutTerminator` reports them and `build.confirmPrefixesWithoutTerminator` owns the prompt, logging a refused prefix before returning `ErrPrefixRejected`. Both checks see `--prefix-maps` applied first, so a mapping is how a project reconciles a file it cannot edit.
- Vocabularies are resolved per project, never from a shared cache on the machine. `validate.PinnedVocabularies` owns the pinned vocabulary nodes of `.sal/config.jsonld` in both directions: it records a prefix's namespace against the SHA-256 of the document behind it as an `owl:versionIRI` of `urn:sha256:<hex>`, and stores that document under `.sal/data/blobs` named by the same hash. A `salmodule://` vocabulary is the exception: it is pinned by the git commit hash of the module repository instead, as `urn:git-commit-hash:<hex>` — see below. `LoadPinnedVocabularies` and `Save` use `pkg.PartitionConfigGraph`/`AssembleConfigGraph` to read and write only the nodes carrying `owl:versionIRI`, carrying the project node `importation` owns forward untouched.
    - `.sal/config.jsonld` belongs in git; the documents its pins name do not, since `sal init` gitignores `.sal/data` and they travel with the data product instead. That split is why `push` and `upload` carry them with no changes of their own.
    - Every pinned node carries the vocabulary's namespace IRI as its `rdfs:label`, the human readable name it is known by, which is the same string as its `@id`.
    - `PinnedVocabularies.AppendProvenance` writes the same `rdfs:label`/`owl:versionIRI`/`dcterms:format`/`dcterms:modified`/`rdfs:comment` statements `.sal/config.jsonld` carries directly into a `*rdflibgo.Graph`, so `build` can commit them to the triples table as provenance. It is the only place that shape is duplicated; `nodes` (the config file writer) and `AppendProvenance` (the graph writer) must be kept in sync by hand since one writes JSON and the other writes RDF triples; `pinnedVocabularyComment` is the one place the `rdfs:comment` text itself is generated, shared by both.
    - The pin is keyed by the prefix namespace, not the document URL, since that is what a project declares. `vocabularyDocumentURL` still decides what is dereferenced, and the store memoizes by that URL so two namespaces served by one document are fetched once.
    - A pin whose document is missing or no longer hashes to the pinned version is fetched again rather than failing, since a fresh clone has the lockfile before it has the documents.
    - Nothing is bundled in the binary; a vocabulary that cannot be fetched or parsed is an error. A fetch (`fetchOnce`) is retried `vocabularyFetchAttempts` times with doubling backoff for a network error, timeout, or 5xx/429, and an unreachable host is reported with advice to seed or pin it. A fetched document that does not parse is unpinned again so it is never recorded as the version validated against.
    - `https://schema.org/` is special-cased in `vocabularyDocumentURL`: the namespace serves HTML whatever Accept says, so the vocabulary is fetched from `https://schema.org/version/latest/schemaorg-current-https.jsonld` and pinned against the namespace like any other. The `http://schema.org/` namespace is refused outright, one `validate.InsecurePrefixError` per declaring file naming the file and line (`Validator.InsecurePrefixes`, driven by `httpsOnlyNamespaces`; `Validator.declared` records a `Location` per declaration, found by `declarationLine`), since schema.org defines its terms only under https; the check sees `--prefix-maps` applied first, so mapping the http spelling onto the https one is the fix for a file the project cannot edit.
    - `EphemeralVocabularies` is the store that pins nothing. Validating RDF outside a SAL project uses it, and so do the unit tests, which replace its `Fetch`.
- `sal validate --salmodule` (`ValidateCmd.SalModule`) checks the project as a SAL module on top of the RDF pipeline, and is implied when the module directory holds both `ontology.jsonld` and a `Dockerfile`. `ValidateCmd.moduleDir` is the single directory named on the command line, else the SAL project root, else the current directory; the module namespace comes from the git remote through `salmodule.ModuleNamespaceForRemote`, falling back to a placeholder, since it only decides which terms count as the module's own. `salmodule.CheckModule` builds and runs nothing. It checks that both files exist, validates `ontology.jsonld` against `specs/salmodule-ontology.schema.json` (`schemaProblems`: each violation on the line of the value it is about, with the `errorMessage`/`patternErrorMessage` the schema annotates the rule with, and for a choice of forms the form that failed deepest rather than every form's reason), reports every term of the module's namespace the document refers to without declaring it with an `@id` and an `@type` (`undeclaredTerms`), every key JSON-LD would drop because it is neither prefixed nor defined in `@context`, every ill-formed named shape as goRDFlib's `shacl.CompileShapes` under `WithStrictShapes` reads them (an inline shape is a blank node the schema has already reported on its own line), and every `stdoutShape` or `stderrShape` constraint `StreamValidator` would refuse at run time that the schema did not already. Every line comes from one scan of the JSON tokens (`scanOntologySource`: JSON pointer to line, plus where each term is first written and where it is declared), not from the JSON-LD parser, whose provenance covers only named subjects. Both sets of problems are returned together as one `validate.MultiError`, each a `salmodule.ModuleError` naming the file and line.
- A `salmodule://` prefix is a vocabulary like any other, but it is not served over HTTP. It is dereferenced by cloning the module repository, building its Dockerfile, and running the module's ontology command; the JSON-LD the module prints is the vocabulary document.
    - The module ontology's relative terms resolve against the module's own `salmodule://` namespace, not against the sal project's base. `vocabularyCache.parseBase` is what keeps these apart; passing the project base here would make every module term fail to match.
    - A `salmodule://` vocabulary is pinned by the git commit hash of the module repository's HEAD at clone time, not by the SHA-256 of the ontology document `PinnedVocabularies.Pin` would otherwise derive. `salmodule.Resolver.image` reads the hash with `git rev-parse HEAD` right after cloning, and `FetchOntologyDocument` reports it alongside the document so `validate.fetchVocabularyDocument` can pin it at `urn:git-commit-hash:` instead of `urn:sha256:`. The reason is that a module's task logic can change without its ontology document changing, and that is a change a build should still be able to tell apart. The document itself is still stored under `.sal/data/blobs`, just named by the commit hash rather than a content digest, so it cannot be re-verified against its pinned version the way a SHA-256 pin can; its presence on disk is trusted instead.
    - This means validating a file that references a module clones and builds that module. That is intended, and matches the dereferencing sequence in the SAL Module spec. Once the project has pinned the ontology the module reported, a later build resolves it from the pin instead of building the module again to ask.
    - Validation never runs module tasks. Only `build` invokes the run command. A task's output is data rather than vocabulary, so materialization is never resolved from a pin.

### `clone`

- Takes in a full URL to an OCI artifact. 
- It uses the oras golang to introspect the manifest info about the artifact. It retrieves the value of the `org.opencontainers.image.source` to determine the location of the source code. It finds the pinned commit hash using the value of `sal.git-commit-hash`.
    - It then clones the source code into the current working directory.
    - It checks out the commit hash specified in the manifest.
    - Within the newly cloned repo directory, it should run `sal init` to initialize a sal project.
    - Within the new cloned repo directory, it should pull the OCI artifact and place it in the `.sal/data` directory.
    - `sal init` is run as a subprocess (`clone.initializeSALProject`, through the `commandRunner` tests fake) with `--description` taken from the artifact's `sal.description` annotation, which `push` writes from the project node of `.sal/config.jsonld` (`push.projectDescription`), falling back to one naming the registry repository for an artifact pushed before that annotation existed (`clone.projectDescription`); nothing is at the prompt to answer for a description otherwise.
    - `sal pull` (`clone/pull.go`, `RunPull`) shares the command struct. Outside a SAL project (`pkg.SalDataDir` is `ErrSalDirNotFound`) it initializes the current directory through `clone.initializeEmptyDirectory`, which refuses a directory holding anything (`ErrDirectoryNotEmpty`), runs `git init`, adds the manifest's `org.opencontainers.image.source` as `origin` so the project name and base match what the artifact was built under, and runs the same `sal init` as clone; no source is checked out. The step is the `clone.init` span, a phase of the pull plan that is skipped inside a project.
    - `pkg.pullLayer` fetches each layer up to `pullAttempts` (4) times, waiting `pullRetryBackoff` doubled per attempt (a var tests zero), since the registry client's own retry covers a failed request but not a body that drops partway (an HTTP/2 `PROTOCOL_ERROR` mid-copy on a long pull); a failed attempt's bytes are taken back with `Transfer.Discard` so the pane counts them once, and `file.ErrDuplicateName` on a retry means the earlier attempt wrote the file, so it counts as pulled.

### `edit`

- Opens the browser form that edits a SAL module's `ontology.jsonld`, the same form `sal init --salmodule` creates it with, in the module the current directory is (`edit.ErrNotAModule` when there is no `ontology.jsonld`). `edit.Form` is the server both commands share and `serve.ModuleFormUI` the embedded page (`serve/sal-ui/salmodule.html`, sources under `serve/sal-ui/src/init/`): `GET /api/module/status` reports the mode (`init` or `edit`), whether the file exists and its current text, and whether a Dockerfile exists; `POST /api/module/validate` runs `salmodule.CheckOntologyDocument` over the posted text; `POST /api/module/write` writes it, creating or replacing the file, with the scaffold files beside it where missing, and refuses with 409 when the file no longer holds the `base` text the form loaded, so a hand edit made while the page was open is never written over. The form (`document.ts`) parses an existing document into a draft losslessly, keeping context entries that are not prefixes, keys it has no field for, and nodes that are neither the ontology node nor a task class, and shows a shape as rows (`PropertyRows.tsx`: name, value kind, required, single, description, message) when it holds only what the rows can say and as JSON otherwise; `dirty` compares against the file's canonical rendering so a differently formatted file is not "edited" until it is.
- `edit.AgentPrompt` renders, from the JSON of the document rather than its RDF (the JSON Schema fixes the shape), the prompt a user hands a coding agent to implement the module: namespace, prefixes, each task with its configuration properties, output and input shapes, and a sample task instance in the serialization `TaskInstance` produces, the run command's contract, and the test commands. It points at the `salmodule` skill files `pkg.InstalledSkills` finds in the module, or says how to install them. `sal edit --prompt` prints it for the file on disk, and `sal edit --agents` (`edit.WriteAgentsFile`) writes it as the module's `AGENTS.md` headed by `agentsMarker`, which is what lets sal write it again; an `AGENTS.md` without the marker is someone's own and is `ErrForeignAgentsFile`. The form shows nothing about the prompt or `AGENTS.md`: with the skill installed the contract is already in the repository, and the prompt is a terminal affair.

### `rewrite`

- Rewrites Iceberg table metadata so a built table can be read from a new table root. It was `sal edit` before the module form took that name.
- `rewrite.RewriteIcebergTableRoot` must update every Iceberg metadata file that can contain paths: `*.metadata.json`, manifest list Avro files, and manifest Avro files.
    - JSON metadata contains fields such as `location`, `manifest-list`, and `metadata-file`.
    - Avro metadata contains fields such as `manifest_path` and data file `file_path`.
- The rewrite command must not rewrite Parquet data files. It only changes metadata references.
- Path rewriting is prefix based: the old table root is replaced by the new table root, and child paths under the old root are preserved.
- `rewrite.RewriteIcebergMetadataPath` exists for upload-time metadata renames. Use it when a single metadata object name changes and every reference to that exact metadata path must be updated.

### `upload`

- upload copies `.sal/data` to a temporary staging directory, rewrites the staged Iceberg metadata, and uploads the staged files. The local `.sal/data` directory must remain unchanged.
    - `stageProjectConfig` also copies `.sal/config.jsonld`, which sits beside `.sal/data`, to the top of the staged copy, so a bucket-root upload carries the project's title, description, and pins for `sal serve --data`. It does nothing for a data directory that is not a project's `.sal/data`.
- upload uses the rewrite package for Iceberg metadata rewrites. Do not duplicate JSON or Avro metadata traversal logic in upload unless the rewrite package cannot represent the operation.
- Bucket URL semantics are important:
    - A bare object-store bucket like `gs://my-bucket/` uploads the full `.sal/data` layout. If the local table is `.sal/data/sal/triples`, the uploaded table root is `gs://my-bucket/sal/triples`.
    - An explicit object-store path or prefix like `gs://my-bucket/sal/triples` or `gs://my-bucket?prefix=sal/triples/` is treated as the table root when there is exactly one Iceberg table.
    - `https://storage.googleapis.com/<bucket>/...` is a supported GCS-compatible URL form. upload must upload through the GCS blob driver but write `https://storage.googleapis.com/<bucket>/...` paths into Iceberg metadata so S3-compatible tooling can resolve the table through HTTPS.
    - Multiple Iceberg tables always preserve their relative table paths under the bucket root or prefix.
- Upload ordering matters for readers: data files first, metadata files second, and `metadata/version-hint.text` last.
- Object-store uploads (`gs`, `s3`, `azblob`, and `https://storage.googleapis.com`) must use fresh metadata object names during upload. Reusing the same Avro manifest object names can leave DuckDB or HTTP/object-store caches reading stale manifests after a reupload.
    - Fresh upload metadata includes renamed Avro metadata files, updated references to those renamed files, a new `v<number>.metadata.json`, and a `version-hint.text` pointing to that version.
    - `version-hint.text` must not include a trailing newline; DuckDB treats the newline as part of the version string.
- Percent escaping depends on the table root scheme:
    - Do not percent-escape Iceberg `file_path` values for `gs://`, `s3://`, or `azblob://` metadata roots. The object-store client handles URL encoding when fetching the object.
    - Do percent-escape child path suffixes for literal `http://` or `https://` metadata roots. Local partition directory names may contain literal percent-encoded values like `predicate_partition=http%3A%2F%2Fschema.org%2Fte`; in an HTTPS URL these percent signs must become `%25` so the remote object key resolves correctly.
- The key upload verification query is:

```sql
SET enable_object_cache = false;
SELECT
    subject,
    predicate,
    object
FROM iceberg_scan(
    'gs://sal-test-bucket/sal/triples'
)
LIMIT 5;
```


### `terraform`

- Writes, and never applies, a Terraform configuration under `terraform/` (`terraform.Generate`, templates in `terraform/terraform.go`) that serves the data product on Google Cloud: a regional Cloud Storage bucket holding the copy of `.sal/data` that `sal upload --bucket gs://<bucket>/` writes, a service account with `objectViewer` on it, and a Cloud Run v2 service running the sal image as `sal serve --data /mnt/sal` with the bucket mounted read-only through Cloud Storage FUSE at `terraform.MountPath`. The FUSE mount is what keeps credentials out of it: DuckDB reads the Iceberg table as local files, so no HMAC key for `gs://` is needed. The defaults are deliberately small (one CPU, 2Gi, min 0, max 2, concurrency 20, UI off because `/api/sql` runs arbitrary DuckDB) and every one is a variable. A file the directory holds is `terraform.ErrExists` unless `--force`; `sal init --with-iac` writes the same files. Nothing here is tested against Google Cloud; `terraform_test.go` checks the generated text.

### `serve` 

- Starts a local HTTP server on port 8080.
- `--data DIR` serves a copy of a project's `.sal/data` instead of the project the current directory belongs to, which is what the Cloud Run service `sal terraform` deploys runs. `salsparql.LocateDataDirTable` finds the one table under it at any depth (`rewrite.IcebergTablePaths` is `pkg.IcebergTablePaths` plus an error for none, so `sal upload`, `sal rewrite`, and `serve` agree on what a table is; tables under `blobs/` and `imports/` are skipped) and names it by path alone (`Warehouse` empty, so `Runner` verifies it through DuckDB like a table on object storage and `allow_moved_paths` reads it wherever its metadata says it was written). It serves all three layouts: a copy of `.sal/data` or a bucket-root upload (`<project>/triples` with `blobs/`, `stac/`, `config.jsonld` at the top), and an explicit-table-root upload (the table at the directory itself). `TriplesTable.DataRoot` (`dataRoot`) is the nearest directory from the table up to the one named that holds `blobs/` or `stac/`; the blob and STAC directories are beside it, and `DuckDBRunner.DataRoot` makes `projectFiles` read `config.jsonld` and `blobs/` from there instead of from a `.sal` project (so `Vocabularies`, the Stats title and vocabulary listing, and `Project` work with no git repository; `standaloneBase` stands in for the remote). Every Iceberg table function reads with `allow_moved_paths = true` (`iceberg_scan`, `iceberg_metadata`, `iceberg_column_stats`), since an uploaded table's metadata names absolute `gs://` paths that a copy must not follow. A data directory with no `config.jsonld` lists only the built-in vocabularies and logs a warning. `upload/serve_copy_test.go` uploads a real table to a fake bucket root and serves it back; keep it passing.
- The server can resolve SPARQL queries against the iceberg triples table
    - The same SPARQL Protocol query operation is also served at `/v{snapshot}/sparql`, where `{snapshot}` is an Iceberg snapshot ID, reading the table as it stood at that snapshot. `salsparql.SnapshotRunner` is the surface it needs on top of `Runner`: `HasSnapshot` asks `iceberg_snapshots()` on every request rather than caching, so a snapshot a build commits while the server runs is queryable without a restart, and `AtSnapshot` returns a `DuckDBRunner` with `SnapshotID` set. A snapshot the table does not have, or a version that is not a snapshot ID, answers 404.
    - A snapshot runner's `Translate` scans `iceberg_scan(<table>, allow_moved_paths = true, snapshot_from_id = N)` in place of the `triples` view for every triple pattern (`tableSources.source` in `translate.go`, which also resolves the endpoint a `SERVICE` names), rather than registering a view per snapshot, so the translated SQL says which snapshot it reads. `ToSQL` itself is unchanged; `toSQL` is the same translation over any source.
    - A `SERVICE <endpoint> { ... }` clause is supported only when the endpoint is one of this server's own, recognized by path alone (`/sparql` or `/v{snapshot}/sparql`, in `translate.go`'s `servicePath`, which must agree with the routes `serve` registers): its triple patterns scan the table at that snapshot while the rest of the query scans the runner's own, so one query joins and compares two snapshots. Nothing is fetched over HTTP, and any other endpoint is an error rather than a federated query. goRDFlib rejects `SERVICE` at parse time but parses `GRAPH`, so `rewriteService` turns `SERVICE <iri>` into `GRAPH <urn:x-sal-service:iri>` before parsing and `basicGraphPatternParts` reads the marked `GraphPattern` back as a service; an unmarked `GRAPH` stays unsupported. The SPARQL tab's **Added since previous snapshot** and **Removed since previous snapshot** samples are built in `SparqlTab.tsx` from the Stats snapshot listing, since they need a snapshot ID only the server knows and the page's own origin for the endpoint IRI.
    - `MINUS { }` and `FILTER [NOT] EXISTS { }` translate to an `EXISTS` subquery correlated to the enclosing query through shared variables (`translator.subquerySQL`), which is what makes a snapshot diff possible; a join cannot express "absent from the other snapshot" and pairs every value of a multi-valued predicate with every other. A subject or predicate correlates by column, an object by rendered text plus `object_language` and `object_type` under `IS NOT DISTINCT FROM`, and a whole `?s ?p ?o` pattern against one enclosing scan by `triple_hash` alone (`correlationSQL`), which is exact and needs no spatial load. `translator.graphPatternParts` flattens a group into `groupParts`: triples, filters, `minusGroup`s and `optionalGroup`s that remember the variables of the group before them, UNION arms, BINDs, VALUES, and subqueries, since the parser nests `{ A MINUS { B } C }` as `Join(Minus(A, B), C)` and SPARQL subtracts B from A alone; a MINUS sharing no variable subtracts nothing, and its filters see only its own variables, whereas EXISTS is correlated on and its filters see everything in scope. A group nested inside a SERVICE is read from that endpoint by wrapping it in the marked `GraphPattern` again (`scopeExists`, and the same wrapping for the optionals, union arms, and subqueries it holds).
    - `translator.groupSQL` turns a `groupParts` into one `groupSQL`, which is one FROM clause: a scan per triple pattern (`patternSQL`), a derived table per VALUES (`valuesSQL`, `v<n>`), subquery (`querySQL` recursively, `q<n>`), and UNION (`unionSQL`, `u<n>` with the arms' scans as `u<n>_<arm>_<i>`, combined with `UNION ALL`), and a `leftJoin` per OPTIONAL (`optionalSQL`, scans `o<n>_<i>`), then the BINDs and last the filters, in that fixed order rather than the order the query wrote them, since a BIND may read a variable an OPTIONAL bound. An OPTIONAL group's constants, joins, and filters all go in the ON clause with an equality per variable it shares with the pattern before it, so a group of several patterns matches whole or not at all; a variable it shares with a pattern after it joins through WHERE as NULL-or-equal (`joinClause`/`nullableClause`), which is also how a nullable binding joins anywhere. `sqlBinding` says where a variable is read: a scan column (`alias`/`column`), a derived table's column named after the variable (`name`; an object every UNION arm binds as an object keeps its typed columns as `"x.object_iri"` and so on, anything else is `valueColumn` text), or an inlined BIND expression (`sql`/`kind`); `nullable` marks what an OPTIONAL, a UNION arm, or an UNDEF can leave unbound. Read a binding only through `col`, `expr`, `projection`, `numeric`, and `present`, never by pasting `alias + ".object_x"`, so a derived binding works wherever a scan does; the alias-string helpers `bindingExpr`/`objectTextExpr`/`timeTextExpr` exist for the hand-written SQL in `resources.go`, `stats.go`, and `export.go`.
    - Expressions live in `query/sparql/expr.go`. `translator.exprSQL` translates a FILTER, BIND, projection, GROUP BY, HAVING, or ORDER BY expression to a `sqlExpr` carrying its `exprKind`, and the kind of the other side is what picks the typed column an object variable is compared in (`comparisonSQL`/`objectComparison`: numeric, `object_time`, `object_string`, `object_iri`, else the rendered text), which is why `FILTER(?age > 21)` never compares text. `numericSQL`, `stringSQL` (reads `object_string`, so a string function on an IRI is NULL as SPARQL says), `termSQL` (STR and casts: the projection, geometry as WKT), and `dateTimeSQL` are the typed readers; `functionSQL` is the builtin table, with aggregates in `aggregateSQL` (MIN/MAX of an object try the numeric columns first, which is why their text is `30.0`), XSD casts in `castSQL` as `TRY_CAST`, and anything else handed to `geoFunctionSQL`, which now returns a `sqlExpr` too. A COALESCE or IF whose branches disagree in kind renders every branch as text (`sharedKind`), since SQL will not mix a number with a string. `sparql-engine.mdx` lists every supported construct and function; keep its tables in step with `functionSQL`.
    - `features_test.go` runs the translated SQL against an in-memory DuckDB `triples` table rather than only comparing text. It loads no extension: `object_geometry` holds WKT text and two macros stand in for `ST_AsText` and `ST_GeomFromText`, since a unit test must not download the spatial extension (CI has no cache of it; `LOAD spatial` fails there).
    - `serve.snapshotSparqlHandler` matches `^/v([^/]*)/sparql$` by hand on the root route and falls through to whatever else the root serves. It is not a ServeMux pattern because a wildcard has to be a whole path segment, so it cannot carry the `v`, and a bare `/{version}/sparql` conflicts with the `/blobs/` prefix. There is no UI tab for the versioned route, so with `--with-ui` it is the API whatever asked for it.
- The triples table is also served as OGC API Features at `/ogc`, with or without `--with-ui`, implementing the Core and GeoJSON conformance classes of Part 1: the landing page, `/ogc/conformance`, `/ogc/collections`, the one collection `/ogc/collections/triples`, its `items`, and `items/{id}`. `serve/features.go` owns the routes (`featuresAPI`; every route goes through `featuresAPI.route`, which sets CORS, refuses unknown query parameters with 400 as Core requires, reads `f`, and writes errors as `{"code","description"}`), and `query/sparql/features.go` owns the SQL (`featuresSQL`) and the `FeatureRunner` interface (`Features`, `FeaturesExtent`, `Project`) that `DuckDBRunner`, `tableSwitch`, and the test fakes implement; `EndpointRunner` is what `NewEndpoint` takes. A feature is an RDF subject with a geometry-valued object and its id is the subject IRI, so the same feature is addressable at every snapshot; when that subject is the object of `geo:hasGeometry`/`geo:hasDefaultGeometry` the feature is that triple's subject instead (`geometryOwnerPredicates`), which is what keeps a GeoSPARQL feature under its own IRI rather than its blank geometry node's. - `DuckDBRunner.Stats` caches what it reads from the table (counts, snapshots, properties, layout) process-wide in `tableStatsCache`, keyed by table path and the metadata file `latestMetadataFile` names, so a refresh of the Stats tab costs one read of the version hint until a build commits a new metadata file; concurrent requests share one read through `singleflight`, a failed read is not cached, and a glob (a local table without a version hint) is never cached. - DuckDB execution and the SQL behind each `sal query --info` option live in `query/sparql`, not in `serve` or `query`. `salsparql.InfoSQL` and `DuckDBRunner.RunSQL`/`Stats`/`Geometries` are shared by the `query` subcommand, the SPARQL shell, and the serve endpoints. Do not duplicate those queries.
    - DuckDB is the `github.com/duckdb/duckdb-go/v2` library linked into the binary, not the `duckdb` CLI shelled out to. Nothing in sal may exec `duckdb`; there is no CLI to find. `query/sparql/duckdb.go` owns the whole surface: the shared handle, the `triples` view, extension loading, and reading rows.
    - `triples` is the whole table: every row is a statement the project makes. There is no reasoning switch anywhere in the query path. RDFS reasoning is a property path over `rdfs:subClassOf`, `rdfs:subPropertyOf`, `rdfs:domain`, or `rdfs:range` (see property paths below), and it walks exactly the rows the table holds, so a hierarchy is walkable only when the project asserted it or imported the ontology stating it with `owl:imports`. `tableSources.source` is the one place that decides what a pattern scans, `triples` or the inline `snapshotScanSQL` for a snapshot, and it decides it by the pattern's `SERVICE` alone, never by its predicate.
    - The library is cgo, so `CGO_ENABLED=0` cannot build sal. The DuckDB library itself is linked statically, but the binary is not fully static: DuckDB `dlopen`s its extensions, which a statically linked glibc cannot do, so libstdc++ and glibc stay dynamic.
    - `duckdbInstance` is the process-wide handle every query runs through, opened on first use. Opening DuckDB and loading its extensions costs far more than any query sal runs, so a process pays for it once. Do not open a second handle per query or per request; `sal serve` answers everything on this one. The Stats tab's subject and object counts are `approx_count_distinct`, not `COUNT(DISTINCT)`: an exact count over tens of millions of terms holds them all in a hash table, which got a Cloud Run instance killed on every visit to the Stats tab.
    - Extensions are downloaded from extensions.duckdb.org on first use, since only `parquet`, `json`, `icu`, and `core_functions` are linked in. `sal duckdb-extensions` primes that cache; it is hidden from help and exists for the Dockerfile and the demo recordings to call.
    - `RunSQL` wraps every statement in `SELECT COLUMNS(*)::VARCHAR FROM (...)` so DuckDB renders each value to text itself. The driver returns Go values, and `GEOMETRY`, `DECIMAL`, `LIST`, and `STRUCT` have no Go equivalent that formats the way DuckDB does. Do not hand-roll that formatting in Go. The wrapper preserves both the inner statement's column names and its `ORDER BY`, which `InfoSQL("snapshots")` depends on.
    - Statements run one after another on the shared handle. There is no batching layer any more: `RunSQLBatch` existed only to amortize process startup across `Stats`'s four queries, and with DuckDB linked in there is no startup left to amortize.
    - The spatial extension is loaded on demand, not at open. It is around 60 MB and DuckDB cannot autoload it. `needsSpatial` decides: the `ST_` functions need it, and so does anything projecting the `object_geometry` column, which DuckDB exposes as `GEOMETRY` and cannot read without it. A statement that needs spatial in some way `needsSpatial` misses is retried once with it loaded, so widening the check is a performance fix, never a correctness one. Once loaded it stays loaded for the life of the process.
- SPARQL is answered by translating it to SQL in `query/sparql/translate.go`. `DuckDBRunner.Translate` is the one place the whole SPARQL-to-SQL step lives, `ToSQL` plus the runner's own `LIMIT` when the query states none; `Run`, the shell's F2 page, and `/api/sparql/translate` all go through it, so the SQL shown anywhere is exactly the SQL that runs. `geosparql.go` maps the GeoSPARQL `geof:` functions that have a direct DuckDB spatial analog (the `sf*` relations, `distance`, the geometry constructors, and GeoSPARQL 1.1's measures, `buffer`, and geometry properties and serializations, each in a table keyed by lowercased local name with the kind it yields) to the `ST_` function of the same meaning; a function without one is an error, never an approximation (`geofUnsupported` carries the reason where there is one: `relate`, since the spatial extension has no DE-9IM function, and `transform`). A unit argument is `uom:degree`, the stored coordinates, or `uom:metre` (`metricUnit`), which the `metric*` forms imply; a measure in metres is the `_Spheroid` function and a buffer in metres is drawn in Web Mercator at the scale of the centroid (`bufferSQL`), the same approximation `metreDistanceSQL` makes. The one translation that is not a single function is `geof:distance` in `uom:metre` (`metreDistanceSQL`): DuckDB's `ST_Distance_Sphere` takes points only, so the nearest points of the two geometries are found with `ST_ClosestPoint` in Web Mercator and the spherical distance taken between them, which is exact between points and works between any geometries; a per-row azimuthal `ST_Transform` would be exact everywhere but builds a PROJ transformation per row and took minutes over twenty thousand rows. The spatial extension is loaded with `SET geometry_always_xy = true`, since every geometry sal stores is longitude then latitude and DuckDB 2.0 refuses the axis-order-sensitive functions until told which order to assume. A projected object renders `object_geometry` as WKT through `ST_AsText`, which is what loads the spatial extension; joins and comparisons keep the geometry-free `bindingExpr` so they never do.
    - `ToSQL` translates SELECT, CONSTRUCT, and ASK; DESCRIBE is not parsed, and `GRAPH` is refused since the table holds one graph. `translator.querySQL` is the per-query step a subquery recurses through: the group, then GROUP BY (a grouped object variable is projected by `expr`, without geometry, so DuckDB sees the grouping expression), the projections (an `(expr AS ?x)` is bound under its name so HAVING and ORDER BY can read it), HAVING, DISTINCT, ORDER BY (`orderBySQL`: an object variable by its numeric columns, then `object_time`, then text), and `limitsSQL`. An ASK is `SELECT EXISTS (...) AS "ask"`; `salsparql.IsAsk` is how `serve` knows to answer `{"head":{},"boolean":...}` instead of bindings. A CONSTRUCT's WHERE clause is translated exactly as a SELECT's is, and `constructSQL` in `query/sparql/construct.go` takes over from the projection: a `solutions` CTE projects every variable the template uses, a variable bound as an object as the nine columns `constructObjectColumns` names so its datatype and language survive, and each template triple is one `SELECT` over it (`templateTripleSQL`), combined with `UNION` since a graph holds a triple once. The rows come back in `ConstructColumns`, which is `ExportSQL`'s column order on purpose, so that `export.ObjectTerm` reads either. A triple a solution makes invalid, a literal subject or a predicate that is not an IRI, is filtered out with `IS NOT NULL` rather than failing the query. A template blank node (`_:b`, or the `?_bnode`/`?_coll` variables the parser generates for `[ ]` and `( )`) is named from an md5 of the values the solution binds, never from a row number, so the same data always constructs the same node and a rebuild stays a no-op. `LIMIT` and `OFFSET` sit inside the CTE, bounding solutions; ORDER BY is dropped, since a graph has no order. `DuckDBRunner.Construct` translates with the runner's own `Limit` zeroed and streams the rows through `StreamSQL`. The shell and `serve` show a CONSTRUCT as a table of those columns; neither serializes RDF.
    - Property paths live in `query/sparql/paths.go`. `translator.pathSteps` reduces a `paths.Path` to `patternTriple`s each carrying a `pathStep`: a top-level sequence becomes patterns chained through hidden `?__sal_path<n>` variables, which `patternSQL` keeps out of `discovered` so `SELECT *` never projects them; everything else is one step from `stepOf`. A simple step is a predicate set in one direction (predicates, negated, inverse): an inverse swaps which column the subject and object read, an alternative of plain IRIs or a negated set is `predicate IN`/`NOT IN` (`predicateClause`), and `!(p|^q)` arrives from the parser as an alternative of a negated set and an inverse negated set. A compound step (`parts`, `alternative`) is what one scan cannot answer, a mixed alternative like `p|^p` or any sequence or alternative inside a repetition, and scans `pathStep.edgesSQL`, a derived table of `start`/`finish` rows that joins the parts of a sequence through the node they share or unites the arms of an alternative; a zero-length part of a sequence (`(a/b?)+`) is expanded away, `a` united with `a/b`, since inside a sequence it has no identity of its own. A repeated step of either kind scans `closureSQL`, the closure of its edges from a recursive CTE (`UNION`, which terminates cycles), plus for `*` and `?` the identity of the endpoint already bound (`closureIdentity`: a constant, or an earlier or enclosing scan's expression joined `LATERAL`), falling back to the nodes the edges touch; the identity row is `UNION`ed in so a cycle back to the start matches once. A repetition of a repetition wraps the inner closure as a one-armed alternative, and the CTEs of a nested closure are named by depth (`edges1`/`closure1`) so they never shadow the outer ones. The CTE sits inside the derived table so the outer `SELECT` stays first, which the `SELECT DISTINCT` rewrite and `textQuery`'s wrapper rely on. The closure is computed whole, correct but potentially slow over a large instance predicate. goRDFlib parses `(^p)+` but not `^p+`.
- `sal query` opens the `query/sparql` shell in SQL mode, and `sal query --sparql` opens the same shell in SPARQL mode. `shellMode` is the only difference: it selects the editor's language and highlighter, its history directory, and whether the F2 page showing the translated SQL exists. SQL mode runs the statement it opened on so that `sal query --info snapshots` shows the snapshots straight away.

- `.github/workflows/release.yml` publishes a GitHub Release on every push to `main`: the `tag` job tags the commit with the next patch version after the newest `v*` tag (`v0.1.0` when there is none; push a `v<major>.<minor>.0` tag by hand to start a new series), the `ui` job builds `serve/sal-ui/dist` once, the `build` matrix compiles sal natively on `ubuntu-latest` (linux/amd64) and `macos-15` (darwin/arm64) with that UI embedded and `-ldflags "-X main.version=<tag>"`, which `sal --version` prints (`args.Version`, falling back to the module version `debug.ReadBuildInfo` records for a `go install` and to `dev`), and the `release` job attaches `sal_<os>_<arch>.tar.gz` and `checksums.txt` with generated notes. ## Telemetry

- `pkg/telemetry` owns OpenTelemetry. `main` calls `telemetry.Setup` once and flushes through the returned function on every exit path, including the `os.Exit` ones, since a span is lost if the process ends before the batch processor sends it. Nothing is exported unless the standard `OTEL_*` variables configure an exporter, so a plain invocation only pays for no-op spans; `docs/src/content/docs/reference/telemetry.mdx` documents the variables, every span, and the metrics.
- Spans are recorded only around the steps that take time, not around everything, and a context is threaded only as far as those steps need it: module resolution and task runs (`salmodule.Resolver`), validation and vocabulary loading (`validate.Validator`, `vocabularyCache.loadTerms`), imports, the Iceberg diff, write, and commit (`build/load`), the CONSTRUCT queries (`build.construct` around the staging and the queries of a build, `construct.query` and `sparql.construct` per query), and queries (`DuckDBRunner.RunSQL`/`Run`). `BuildCmd.Run` starts the root span of a `sal build`, `sal run`, or `sal validate` trace (`fromRunCmd` is what names the run trace), `ConstructCmd.Run` the root span of a `sal construct` trace, `PushCmd.Run`, `RunPull`, and `RunClone` the root spans of `sal.push`, `sal.pull`, and `sal.clone` (with `oci.fetch_manifest`, `oci.push_layers`, `oci.push_manifest`, `oci.pull_layers`, and the `clone.*` git steps under them), and `serve.instrument` wraps the HTTP handler with `otelhttp` so each request is a server span. Add a span with `telemetry.Start` and a deferred `telemetry.End(span, err)` over a named error result, so a failure is the span's status; give it the `sal.` prefixed attributes the docs page lists rather than inventing a new vocabulary.
- A transfer is the one kind of span that changes while it runs: `pkg.Transfer` counts the files and bytes an OCI push or pull has moved and writes them onto the `oci.push_layers`/`oci.pull_layers` span as `sal.oci.files`, `sal.oci.bytes`, `sal.oci.files_done`, and `sal.oci.bytes_done` (every 256 KiB and on every file), and logs every five files, with the average speed, for a run with no pane; the pane computes the speed itself from the step's start and `bytes_done`. A push or pull moves `--parallel` files at once (`pkg.DefaultParallelTransfers`, 16; `PullManifestLayers` takes it as a parameter, 0 for the default), since the files are small and request latency dominates. A pull counts through `Transfer.Reader` over each fetched layer; a push counts through `Transfer.Transport` on the registry client (`pkg.CountUploads` copies the client rather than changing the shared `auth.DefaultClient`), since oras buffers a pushed blob before sending it, so the reader handed to it says nothing about the upload, and a body sent again after an auth challenge is counted again, which the pane clamps.
- `pkg/progress` is the pair of panes `main` opens for the commands `progress.Plan` knows (`build`, `run`, `push`, `pull`, `clone`; `progressCommand` in `main.go` is where a command joins them, each with a `--no-tui`). Bubble Tea queries the terminal when the panes open and the terminal answers on stdin, so the panes stay up for `minimumShown` even when the work ends at once; quitting sooner leaves the shell to print the answers as stray escape sequences. The tracker is a span processor; a running step's attributes are re-read off its live `ReadWriteSpan` on every draw (`Tracker.refresh`), which is how a transfer's bar moves without the span ending, and `describe` is the one table naming every span and what its attributes say. A phase of the plan can name a root span attribute (`Phase.SkippedAttribute`) that says why the command decided there was nothing for it to do, which the pane then shows as done with that reason rather than skipped and `UI.Summary` carries in its headline: `sal pull` writes `pkg.PullSkippedAttribute` (`sal.pull.skipped`, "up to date, nothing to pull" or that the local data product is ahead) on `sal.pull` when `SnapshotDiff` reports `ErrNothingToPull`.
- Metrics are the `contrib/instrumentation/runtime` and `host` instrumentation (Go memory, goroutines, process and system CPU and memory) plus `otelhttp`'s request duration; sal defines no instruments of its own. Tests that need to see spans set a `tracetest.SpanRecorder` as the global tracer provider and restore it afterwards.

## Code Style

- Use testify for writing succinct tests; avoid just the standard library and if statements with `t.Error()`.
- If a function would only be called from one other function and it is short, try to just condense it into the function that calls it.
- Any function with functionality that is non trivial should be documented with a succinct comment of what it does.
- Don't create functions that are very small and only used in a single place.
- Prefer to not use table oriented tests unless there is significant test duplication; make each test case a separate test function so it is easier to debug and isolate failures.
- All tests should be unit tests without external fetches to remote servers. All local filesystem operations should be mocked or written to tmp files. 

## Boundaries

* Ask First:
    - Large cross-package refactors.
    - If some functionality would be very complex, duplicative, and better handled by an underlying library like iceberg-go, json-gold or goRDFlib, explicitly call it out; don't try to create a custom fix here with lots of specialized code if a fix makes more sense upstream.
